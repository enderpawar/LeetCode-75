# [알고리즘 스터디 2주차] 비트 연산으로 생각하기

이번 회차는 비트 연산 문제 두 개를 묶어서 풀었다. 평소에 배열이나 해시맵으로 접근하던 문제를 비트 단위로 다시 보면 코드가 확 짧아진다는 얘기를 들어서, 실제로 그게 어떤 느낌인지 확인해보고 싶었다. 두 문제 모두 "정답 자체는 한 줄인데 그 한 줄이 왜 성립하는지" 설명하는 게 더 어려웠다.

## 1. 136. Single Number - 혼자 남은 숫자 찾기

정수 배열이 주어지는데, 모든 원소가 정확히 두 번씩 등장하고 딱 하나만 한 번 등장한다. 그 하나를 찾아 반환하면 된다. 추가 메모리는 상수만 써야 한다는 조건이 붙는다.

```python
class Solution(object):

    def singleNumber(self, nums):
        """
        :type nums: List[int]
        :rtype: int
        """
        ans = 0
        for num in nums:
            ans ^= num
        return ans
```

XOR의 성질 세 가지가 이 문제를 그대로 풀어준다. `a ^ a == 0`이고, `a ^ 0 == a`이며, XOR은 순서를 바꿔도 결과가 같다. 그러니 배열 전체를 순서 상관없이 XOR로 누적하면 두 번씩 나온 값들은 서로 짝을 지어 0이 되고, 마지막에 남는 건 한 번만 등장한 값과 0의 XOR, 즉 그 값 자체다.

초기값을 `0`으로 둔 것도 그냥 관습이 아니라 XOR의 항등원이 0이기 때문이다. 배열에 원소가 하나뿐인 경우에도 `0 ^ x == x`라서 그대로 답이 된다.

풀면서 걸렸던 부분은 다음과 같았다.

- 처음에는 딕셔너리로 개수를 세는 방법이 먼저 떠올랐는데, 그러면 공간 복잡도가 `O(n)`이 되어 문제 조건을 어긴다. "상수 공간"이라는 조건이 사실상 비트 연산을 쓰라는 힌트였다.
- `ans ^= num`이 `ans = ans ^ num`과 같다는 걸 머리로는 알아도, 누적 XOR이 "짝을 지운다"는 감각으로 연결되기까지 시간이 걸렸다.

시간 복잡도는 `O(n)`, 공간 복잡도는 `O(1)`이다.

## 2. 338. Counting Bits - 0부터 n까지 각 수의 1 개수 세기

정수 `n`이 주어지면, `0 <= i <= n`인 각 `i`에 대해 `i`를 이진수로 나타냈을 때 1의 개수를 담은 길이 `n + 1`짜리 배열을 반환한다. `__builtin_popcount` 같은 내장 함수는 쓸 수 없다.

```python
class Solution:

    def countBits(self, n):
        ans = [0] * (n + 1)
        offset = 1

        for i in range(1, n + 1):
            # i가 새로운 2의 거듭제곱(2, 4, 8, 16...)에 도달하면 offset 갱신
            if offset * 2 == i:
                offset = i

            ans[i] = ans[i - offset] + 1

        return ans
```

처음에는 각 수마다 이진 변환을 돌려서 1을 세는 방법을 생각했다. 그러면 수 하나당 `O(log n)`이라 전체가 `O(n log n)`이 된다. 제약이 `10^5`이니 통과는 하겠지만, 손으로 0부터 7까지 이진수를 적어보다가 더 나은 규칙이 보였다.

```
0   0     -> 0
1   1     -> 1
2   10    -> 1
3   11    -> 2
4   100   -> 1
5   101   -> 2
6   110   -> 2
7   111   -> 3
```

4~7 구간은 0~3 구간의 값에 정확히 1씩 더한 모양이다. 당연한데, `4 = 100`이니까 4를 더한다는 건 앞자리에 1을 하나 붙이는 것과 같고 나머지 하위 비트는 그대로이기 때문이다. 그래서 `i`보다 작거나 같은 가장 큰 2의 거듭제곱을 `offset`으로 두면 `ans[i] = ans[i - offset] + 1`이 성립한다. 노트에 "그냥 offset처럼 더하는 식으로 하면 되잖아"라고 적어둔 게 이 규칙이었다.

`offset`은 처음에 1로 두고, 반복문 안에서 `offset * 2 == i`일 때만 `offset = i`로 갱신한다. 즉 `i`가 2, 4, 8, 16...에 도달하는 순간에만 경계가 바뀐다. 예를 들어 `i = 5`면 `offset`은 4이고 `ans[5] = ans[1] + 1 = 2`가 된다. 이미 계산해둔 작은 인덱스만 참조하므로 값이 항상 준비돼 있다는 점에서 DP에 가깝다.

풀면서 걸렸던 부분은 다음과 같았다.

- 처음 작성한 코드에서 `def countBits(self, n)` 뒤에 콜론을 빠뜨려서 실행조차 되지 않았다. 로직을 고민하느라 문법에서 막히는 건 좀 허무했다.
- `offset`을 "현재 구간의 시작점"이 아니라 "지금까지 뺀 값"으로 헷갈려서 갱신 조건을 `offset * 2 == i`가 아닌 다른 형태로 쓸 뻔했다. `i`가 정확히 2의 거듭제곱일 때만 구간이 바뀐다는 걸 표로 확인하고 나서야 정리됐다.

시간 복잡도는 `O(n)`이고, 반환 배열을 제외한 추가 공간은 `O(1)`이다. 결과 배열까지 포함하면 `O(n)`이다.

## 3. 스스로 묻고 답한 질문들

### Q. 136번에서 XOR 대신 덧셈이나 곱셈을 쓸 수는 없나?

덧셈으로는 안 된다. 같은 값을 두 번 더해도 서로 상쇄되지 않기 때문이다. `sum(set(nums)) * 2 - sum(nums)`처럼 집합을 쓰면 답은 나오지만 `set`을 만드는 순간 공간이 `O(n)`이 되어 조건을 어긴다. XOR이 특별한 이유는 "같은 값 두 번이면 0"이라는 자기 상쇄 성질을 가진 연산이기 때문이다.

### Q. 338번에서 `ans[i] = ans[i >> 1] + (i & 1)`로 쓰는 풀이도 봤는데 뭐가 다른가?

원리는 같고 구간을 나누는 방식만 다르다. 오른쪽 시프트 방식은 `i`의 마지막 비트를 떼어내고 나머지의 결과를 재활용하는 것이고, offset 방식은 최상위 비트를 떼어내고 나머지를 재활용하는 것이다. 둘 다 이미 계산된 더 작은 인덱스를 참조하므로 `O(n)`이다. 어느 쪽이든 내장 popcount를 쓰지 않으므로 문제 조건도 만족한다.

### Q. `offset`이 `i`를 앞질러버릴 위험은 없나?

없다. `offset`은 `offset * 2 == i`일 때만 `i`로 갱신되므로 항상 `offset <= i`가 유지된다. 따라서 `i - offset`은 0 이상이고, 동시에 `i`보다 작아서 이미 채워진 칸만 읽는다.

### Q. `n = 0`이면 어떻게 되나?

`ans = [0]`이 만들어지고 `range(1, 1)`이 비어 있어 반복문이 한 번도 돌지 않는다. 그대로 `[0]`을 반환하는데, 0의 이진수에 1이 없으므로 정답이다. 경계 조건이 자연스럽게 처리되는 구조라 따로 분기를 둘 필요가 없었다.

## 정리하며

두 문제 모두 자료구조를 늘리는 대신 "수를 이진수로 보면 어떻게 되는가"를 먼저 물어보는 문제였다. 136번은 XOR의 자기 상쇄 성질 하나로 상수 공간 조건을 뚫었고, 338번은 이진수 표를 직접 적어보다가 구간 반복 규칙을 발견해서 `O(n)`으로 줄였다. 특히 338번은 감으로 규칙을 찾은 뒤에 "왜 그 규칙이 성립하는가"를 최상위 비트 관점으로 설명할 수 있게 된 게 이번 회차의 가장 큰 소득이다.
