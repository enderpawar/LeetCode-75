# [LeetCode 75 Day 10] Dynamic Programming, 공간 복잡도 최적화

LeetCode 75 열 번째 날에는 두 문제 모두 다이나믹 프로그래밍으로 풀었다. N-th Tribonacci Number는 트리보나치 수를 구하는 문제였고, Min Cost Climbing Stairs는 계단을 오르는 최소 비용을 구하는 문제였다. 두 문제 모두 현재 값을 구하기 위해 바로 이전 몇 개의 값만 있으면 충분하다는 점이 같아서, 배열 전체를 저장하는 대신 변수 몇 개만 유지하는 쪽으로 풀이를 다듬어봤다.

## 1. N-th Tribonacci Number - 재귀 메모이제이션에서 변수 세 개로

트리보나치 수열은 $T_0 = 0$, $T_1 = 1$, $T_2 = 1$이고 $T_{n+3} = T_n + T_{n+1} + T_{n+2}$로 정의된다. 정수 `n`이 주어지면 $T_n$을 구하는 문제다.

처음에는 점화식을 그대로 재귀로 옮기고, 이미 구한 값을 클래스 속성 리스트에 저장해두는 방식으로 풀었다.

```python
class Solution(object):

    dp = [0, 1, 1]

    def tribonacci(self, n):
        if n < len(Solution.dp):
            return Solution.dp[n]

        Tn = self.tribonacci(n - 1) + self.tribonacci(n - 2) + self.tribonacci(n - 3)
        self.dp.append(Tn)
        return Tn
```

`Solution.dp`에 이미 계산된 값이 있으면 바로 반환하고, 없으면 재귀 호출로 구한 뒤 리스트 뒤에 이어붙인다. `tribonacci(n - 1)`을 먼저 호출하면 그 안에서 `n - 1`까지의 값이 전부 `dp`에 쌓이기 때문에, 뒤이어 호출하는 `tribonacci(n - 2)`와 `tribonacci(n - 3)`은 이미 저장된 값을 꺼내기만 하면 된다. 그래서 겉보기와 달리 각 `n`에 대해 실제로 새로 계산되는 값은 한 번뿐이고, 전체 시간 복잡도는 `O(n)`이다.

다만 이 방식은 `dp`를 클래스 속성으로 두고 호출할 때마다 계속 늘려가기 때문에, 값을 한 번만 구하고 끝나는 문제에서는 굳이 리스트 전체를 들고 있을 필요가 없다는 생각이 들었다. 그래서 최근 세 개의 값만 변수로 들고 다니는 형태로 다시 작성했다.

```python
class Solution(object):

    def tribonacci(self, n):
        if n == 0:
            return 0
        if n <= 2:
            return 1

        # T_0, T_1, T_2
        a, b, c = 0, 1, 1

        for _ in range(3, n + 1):
            # 세 변수를 한 칸씩 슬라이딩
            a, b, c = b, c, a + b + c

        return c
```

`a`, `b`, `c`는 각각 $T_{i-3}$, $T_{i-2}$, $T_{i-1}$을 가리키다가, 반복문을 한 번 돌 때마다 한 칸씩 밀린다. `a, b, c = b, c, a + b + c`에서 오른쪽 값들이 먼저 전부 계산된 뒤 왼쪽 변수에 동시에 배정되므로, `c`를 갱신할 때 아직 갱신되지 않은 `a`와 `b`를 그대로 쓸 수 있다. 반복문이 끝나면 `c`가 정확히 $T_n$이 된다.

시간 복잡도는 `O(n)`으로 재귀 버전과 같지만, 공간 복잡도는 변수 세 개만 사용하므로 `O(n)`에서 `O(1)`로 줄었다.

## 2. Min Cost Climbing Stairs - 두 계단 전까지의 최소 비용만 기억하기

`cost` 배열이 주어지고, `cost[i]`는 `i`번째 계단을 밟을 때 지불하는 비용이다. 한 번에 한 칸 또는 두 칸을 오를 수 있고, 시작은 인덱스 0 또는 1 중 아무 곳에서나 할 수 있다. 계단 꼭대기, 즉 마지막 계단보다 한 칸 더 위에 도달하기 위한 최소 비용을 구하는 문제다.

```python
class Solution(object):

    def minCostClimbingStairs(self, cost):
        # prev1: 1단계 전 계단까지의 최소 비용
        # prev2: 2단계 전 계단까지의 최소 비용
        prev2, prev1 = 0, 0

        for c in cost:
            # 현재 계단을 밟고 다음으로 넘어가는 최소 비용 계산
            curr = c + min(prev1, prev2)
            prev2 = prev1
            prev1 = curr

        return min(prev1, prev2)
```

`prev2`와 `prev1`을 둘 다 0으로 시작하는 이유는, 시작 지점을 인덱스 0과 1 중 아무 곳이나 고를 수 있어서 그 이전까지 드는 비용이 없다고 보기 때문이다. 반복문에서 `c`는 현재 계단의 비용이고, `curr`은 그 계단을 밟기까지 드는 최소 비용이다. 한 칸 전 또는 두 칸 전에서 올 수 있으므로 `min(prev1, prev2)`에 현재 계단 비용을 더한다.

반복이 끝나면 `prev1`은 마지막 계단까지의 최소 비용, `prev2`는 마지막에서 한 칸 전 계단까지의 최소 비용이다. 꼭대기는 이 둘 중 어느 계단에서도 한 번에 도달할 수 있으므로 `min(prev1, prev2)`가 정답이 된다.

배열을 한 번만 순회하므로 시간 복잡도는 `O(n)`이고, 매 순간 두 변수만 유지하므로 공간 복잡도는 `O(1)`이다.

## 3. 스스로 묻고 답한 질문들

### Q. 재귀 버전에서 `dp`를 클래스 속성으로 둔 이유는 뭘까?

인스턴스 속성으로 두면 `Solution()`을 새로 만들 때마다 메모이제이션이 초기화돼서, 이전에 계산한 값을 재사용할 수 없다. 클래스 속성으로 두면 여러 번 호출해도 `dp`가 계속 쌓여 있어서 다음 호출에서 다시 활용할 수 있다. 다만 이렇게 하면 리스트가 계속 커지고, 문제를 딱 한 번만 풀 때는 이 이력을 남길 이유가 없다. 슬라이딩 변수 버전은 필요한 값만 그때그때 들고 있다가 버리기 때문에 이런 부담이 없다.

### Q. `a, b, c = b, c, a + b + c`처럼 한 줄에 동시에 배정하는 게 왜 필요할까?

만약 이걸 `a = b`, `b = c`, `c = a + b + c` 세 줄로 나눠 쓰면, 세 번째 줄에서 쓰이는 `a`와 `b`는 이미 갱신된 값이라 원래 의도했던 이전 값이 아니게 된다. 파이썬의 튜플 배정은 오른쪽을 먼저 다 계산한 뒤에 왼쪽에 배정하기 때문에, 갱신 전의 `a`, `b`, `c` 값으로 다음 값을 정확히 계산할 수 있다.

### Q. Min Cost Climbing Stairs에서 `prev2, prev1 = 0, 0`으로 둘 다 0에서 시작해도 되는 이유는?

`cost[i]`는 그 계단을 밟을 때 지불하는 비용이지, 그 계단에 도착하는 비용이 아니다. 즉 인덱스 0이나 1에 서 있는 상태 자체에는 아직 비용이 들지 않았고, 그 계단을 밟고 다음으로 넘어갈 때 비로소 `cost` 값을 낸다. 그래서 시작점인 인덱스 0과 1 이전까지의 누적 비용을 둘 다 0으로 두는 게 맞다.

## 정리하며

두 문제 모두 현재 값을 구하는 데 바로 이전 두세 개의 값만 있으면 충분한 구조였다. 트리보나치 수는 재귀와 메모이제이션으로 먼저 풀어보고, 이후 배열 전체 대신 변수 몇 개로 같은 값을 구할 수 있다는 걸 확인하면서 공간 복잡도를 O(n)에서 O(1)로 줄였다. Min Cost Climbing Stairs는 처음부터 두 변수만으로 풀었는데, 두 문제를 나란히 보니 다이나믹 프로그래밍에서 이전 상태를 배열에 전부 쌓아둘지, 필요한 만큼만 변수로 들고 다닐지를 구분해서 생각하는 습관이 조금 더 분명해졌다. 다음에는 이전 상태를 두 개보다 더 많이 참조해야 하는 문제에서도 이 슬라이딩 방식이 그대로 적용되는지 확인해보고 싶다.
