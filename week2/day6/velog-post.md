# [LeetCode 75 Day 13] 11. Container With Most Water & 1679. Max Number of K-Sum Pairs

이번에 푼 두 문제는 유형표에 똑같이 "투 포인터"로 묶여 있지만, 실제로 풀어보니 포인터를 어떻게 움직일지 정하는 근거가 서로 달랐다. 하나는 넓이를 제한하는 낮은 선을 버려야 했고, 다른 하나는 합을 과하거나 모자라게 만드는 끝값을 버려야 했다.

두 문제 모두 처음 떠올린 답은 이중 반복문이었고, 입력 크기를 보고서야 그게 불가능하다는 걸 알고 방향을 바꿨다. 그 과정에서 "전체를 다 보지 않아도 되는 이유"를 스스로 설명할 수 있어야 투 포인터를 쓸 수 있다는 걸 알게 돼서, 그 근거를 중심으로 정리해둔다.

## 1. Container With Most Water — 두 선 사이에 담기는 물의 최대량

높이 배열 `height`가 주어지고, 두 선과 x축이 만드는 용기의 최대 넓이를 구하는 문제다. 인덱스 `i`, `j`에 대해 넓이는 `min(height[i], height[j]) * (j - i)`가 된다.

```python
class Solution(object):
    def maxArea(self, height):
        """
        :type height: List[int]
        :rtype: int
        """
        left = 0
        right = len(height) - 1

        max_width = -1  # 넓이의 최댓값

        while left < right:
            width = min(height[right], height[left]) * (right - left)

            if max_width < width:
                max_width = width

            if height[left] >= height[right]:
                right -= 1
            else:
                left += 1

        return max_width
```

처음에는 모든 쌍을 비교하려고 했다. 공식 자체는 어렵지 않으니 이중 반복문으로 최댓값을 갱신하면 끝이라고 생각했는데, 입력 크기가 10^5까지라 O(N²)은 애초에 통과할 수 없다는 걸 확인하고 접근을 접었다. 정렬해서 큰 값부터 보는 것도 생각했지만, 넓이에 인덱스 차이가 그대로 들어가기 때문에 정렬하는 순간 위치 정보가 사라져서 쓸 수 없었다.

결국 양 끝에서 시작해 안쪽으로 좁혀오는 방식으로 바꿨다. 처음에 `left = 0`, `right = len(height) - 1`로 두면 폭은 가능한 최대다. 이 상태에서 어느 한쪽을 안으로 옮기면 폭은 반드시 줄어드니까, 넓이가 커질 여지는 높이가 올라가는 경우뿐이다. 그런데 높이는 낮은 쪽 선이 결정하므로, 높은 쪽을 옮겨봐야 여전히 낮은 쪽에 막혀서 이득이 없다. 그래서 낮은 쪽을 안으로 옮긴다. 코드에서는 `height[left] >= height[right]`일 때 `right`를 줄이는데, 오른쪽이 더 낮거나 같은 상황이므로 오른쪽을 버리는 것이다. 두 높이가 같을 때는 어느 쪽을 옮겨도 상관없다.

풀면서 걸렸던 부분은 다음과 같았다.

- 처음에 "정렬해서 큰 값끼리 붙이면 되지 않나"라고 생각한 것. 넓이 공식에 인덱스가 들어가는 문제에서는 정렬이 정보를 파괴한다는 걸 놓치고 있었다.
- 변수 이름을 `max_width`로 잡아버린 것. 실제로 담고 있는 값은 폭이 아니라 넓이라서, 나중에 코드를 다시 읽을 때 스스로 헷갈렸다.
- 초깃값을 `-1`로 둔 것. 결과적으로 문제가 없지만(넓이는 항상 0 이상이라 첫 비교에서 바로 갱신된다), 넓이의 하한이 0인 이상 `0`이 더 자연스러운 초깃값이다.

시간 복잡도는 `O(N)`, 공간 복잡도는 `O(1)`이다. 포인터 두 개가 서로를 향해 한 칸씩만 움직이므로 전체 이동 횟수가 `N`을 넘지 않는다.

### 더 개선한다면

복잡도 자체는 이미 `O(N)`이라 더 줄일 여지가 없다. 대신 아쉬운 건 이름과 잔여 연산이다. `max_width`는 넓이를 담고 있으니 `max_area`가 맞고, 갱신도 `max()`로 한 줄이면 된다. 여기에 더해, 낮은 쪽을 옮길 때 그보다 낮거나 같은 선들은 볼 필요가 없다. 폭은 더 줄었는데 높이는 여전히 그 값에 막혀 있어서 넓이가 커질 수 없기 때문이다. 그래서 한 칸씩이 아니라 "더 높은 선이 나올 때까지" 건너뛰게 만들 수 있다.

```python
class Solution(object):
    def maxArea(self, height):
        """
        :type height: List[int]
        :rtype: int
        """
        left = 0
        right = len(height) - 1
        max_area = 0

        while left < right:
            h = min(height[left], height[right])
            max_area = max(max_area, h * (right - left))

            # 낮은 쪽을 버리되, 그보다 높은 선이 나올 때까지 건너뛴다
            while left < right and height[left] <= h:
                left += 1
            while left < right and height[right] <= h:
                right -= 1

        return max_area
```

`[1,8,6,2,5,4,8,3,7]`로 확인해보면 `left=0, right=8`에서 넓이 8을 기록하고 `left`가 1로 이동, 거기서 `min(8,7)*7 = 49`를 잡은 뒤 `right`가 6까지 건너뛰고, 마지막에 두 포인터가 만나면서 49를 반환한다. 다만 최악의 경우(높이가 계속 증가하는 배열)에는 건너뛸 게 없어서 여전히 `O(N)`이고, 안쪽 while이 두 겹이라 "포인터가 한 번에 한 칸 움직인다"는 원래 코드의 단순함은 잃는다. 상수 시간 이득과 읽기 쉬움을 맞바꾼 셈이다.

## 2. Max Number of K-Sum Pairs — 합이 k가 되는 쌍 최대 개수

배열에서 합이 `k`가 되는 두 수를 골라 제거하는 연산을 반복할 때, 최대 몇 번 수행할 수 있는지 구하는 문제다. 한 번 쓴 수는 다시 쓸 수 없다.

```python
class Solution(object):
    def maxOperations(self, nums, k):
        """
        :type nums: List[int]
        :type k: int
        :rtype: int
        """
        left = 0
        right = len(nums) - 1
        pair_num = 0  # 두 개 더해서 값이 k가 나오는 쌍의 개수

        nums.sort()  # 그냥 sort(nums) 아니다. 주의.

        while left < right:
            if k < nums[left] + nums[right]:  # 너무 과해. right를 옮겨
                right -= 1
            elif k > nums[left] + nums[right]:
                left += 1
            elif k == nums[left] + nums[right]:
                pair_num += 1
                right -= 1
                left += 1

        return pair_num
```

앞 문제와 마찬가지로 처음에는 `left`를 고정하고 `right`를 훑는 식을 떠올렸는데, 그건 결국 `n-1 + n-2 + ...` 등차수열 합이라 `O(N²)`이 된다. 그래서 여기서도 양 끝 포인터를 쓰기로 했다.

다만 정렬 없이는 양 끝을 비교하는 게 아무 의미가 없다. 정렬을 하고 나서야 `nums[left]`가 남은 수 중 가장 작고 `nums[right]`가 가장 크다는 성질이 생기고, 그때부터 합을 보고 방향을 정할 수 있다. 합이 `k`보다 크면 가장 큰 수가 과한 것이므로 `right`를 줄이고, 합이 `k`보다 작으면 가장 작은 수가 모자란 것이므로 `left`를 올린다. 합이 정확히 `k`면 두 수를 함께 소비했으므로 개수를 세고 양쪽을 동시에 안으로 당긴다.

버려지는 수가 정말 버려도 되는 수인지 짚어두면, 합이 `k`보다 클 때 `nums[right]`는 남은 수 중 가장 작은 `nums[left]`와 더해도 `k`를 넘는다. 즉 남은 어떤 수와 짝지어도 `k`를 만들 수 없으므로 안전하게 제외된다. 반대쪽도 같은 논리다.

풀면서 걸렸던 부분은 다음과 같았다.

- `nums.sort()`와 `sort(nums)`를 헷갈렸다. `sort`는 리스트의 메서드라 `nums.sort()` 형태로만 쓰고 반환값은 `None`이다. 새 리스트를 받고 싶으면 `sorted(nums)`를 쓴다.
- "`nums[i] >= k`면 건너뛰어야 한다" 같은 예외 처리를 따로 넣어야 하나 고민했는데, 정렬 후 투 포인터에서는 그런 수가 자연스럽게 `right` 쪽에서 먼저 걸러진다. 조건 분기가 이미 그 일을 하고 있어서 별도 처리가 필요 없었다.
- 같은 값이 여러 개인 경우(`[3,3,3]`, `k=6`)가 걱정됐는데, 매칭될 때 `left`와 `right`를 동시에 움직이므로 한 원소가 두 번 쓰이는 일은 생기지 않는다.

시간 복잡도는 정렬이 지배해서 `O(N log N)`, 공간 복잡도는 정렬을 제외하면 `O(1)`이다.

### 더 개선한다면

마지막 `elif k == nums[left] + nums[right]`는 앞의 두 조건을 모두 통과했으면 무조건 참이므로 `else`로 충분하다. 그리고 매 반복마다 `nums[left] + nums[right]`를 최대 세 번 다시 계산하는 것도 아깝다. 더 크게 보면, 이 문제는 사실 "정렬"이 필요 없다. 짝이 되는 값은 `k - x`로 바로 정해지기 때문에, 개수만 세어두면 정렬 없이 한 번의 순회로 끝난다.

```python
from collections import Counter


class Solution(object):
    def maxOperations(self, nums, k):
        """
        :type nums: List[int]
        :type k: int
        :rtype: int
        """
        count = Counter(nums)
        pair_num = 0

        for x, c in count.items():
            partner = k - x
            if x * 2 == k:
                pair_num += c // 2
            elif x < partner:
                pair_num += min(c, count[partner])

        return pair_num
```

`x * 2 == k`인 경우는 자기 자신끼리 짝을 지어야 하므로 개수를 2로 나누고, 그 외에는 `x < partner`일 때만 세어서 같은 쌍을 두 번 세지 않게 했다. `[3,1,3,4,3]`, `k=6`이면 `x=3`에서 `3 // 2 = 1`, 나머지는 짝이 없어 1을 반환하고, `[1,2,3,4]`, `k=5`면 `(1,4)`와 `(2,3)`에서 각각 1씩 더해 2를 반환한다. 시간 복잡도는 `O(N)`으로 줄었지만, 대신 카운터를 위한 `O(N)` 공간을 쓰게 됐다. 정렬 기반 투 포인터가 제자리에서 도는 것과 맞바꾼 부분이다.

## 3. 스스로 묻고 답한 질문들

### Q. 두 문제 모두 투 포인터인데, 왜 하나는 정렬이 필요 없고 하나는 필수인가?

Container With Most Water는 넓이 공식에 인덱스 차이가 들어간다. 정렬하면 그 인덱스가 뒤섞이므로 정렬 자체가 문제를 바꿔버린다. 반면 K-Sum Pairs는 값의 합만 보고 위치는 아무 의미가 없어서, 정렬해서 "가장 작은 값 / 가장 큰 값"이라는 성질을 만들어야 방향을 판단할 수 있다. 정렬 여부는 습관이 아니라 문제가 위치에 의존하는지로 갈린다.

### Q. Container 문제에서 낮은 쪽 대신 높은 쪽을 옮기면 왜 안 되나?

높은 쪽을 안으로 옮기면 폭은 무조건 줄고, 높이는 여전히 반대편 낮은 선에 막혀 있어서 기껏해야 같거나 작아진다. 즉 개선될 가능성이 0인 방향이라 탐색할 이유가 없다. 낮은 쪽을 옮길 때만 "더 높은 선을 만나 높이가 올라갈" 여지가 생긴다.

### Q. `nums.sort()`와 `sorted(nums)`는 언제 나눠 쓰나?

`nums.sort()`는 리스트를 제자리에서 정렬하고 `None`을 반환한다. `sorted(nums)`는 원본을 두고 새 리스트를 만들어 반환한다. `sorted_nums = nums.sort()`처럼 쓰면 `None`이 들어가서 다음 줄에서 바로 터진다. 원본을 보존해야 하거나 정렬 결과를 곧바로 다른 표현식에 넣을 때는 `sorted`, 메모리를 아끼면서 그 자리에서 쓸 거면 `sort`다.

### Q. 변수 이름이 그렇게 중요한가?

Container 문제에서 넓이를 `max_width`에 담아둔 탓에, 조건문을 다시 읽을 때마다 "지금 폭을 비교하는 건가?" 하고 한 번씩 멈췄다. 코드는 맞게 돌아갔지만 읽는 비용이 계속 발생했다. 이름이 값의 의미와 어긋나면 그 오해가 디버깅 시간으로 돌아온다는 걸 짧게 체감했다.

## 정리하며

이번에 푼 두 문제는 겉보기에 전혀 다른데 "전체 비교를 어떻게 피할 것인가"라는 질문에서 같은 답으로 수렴했다. 두 문제 모두 처음 떠올린 건 이중 반복문이었고, 입력 크기를 보고 그게 불가능하다는 걸 확인한 뒤에야 투 포인터로 넘어갔다. 그 과정에서 투 포인터의 핵심이 "양쪽에서 좁혀오는 모양"이 아니라 **지금 결과를 제한하고 있는 쪽을 골라서 버리는 것**이라는 걸 정리할 수 있었다. Container에서는 낮은 선이, K-Sum Pairs에서는 합을 과하게/모자라게 만드는 끝값이 그 대상이었다.

동시에 투 포인터가 항상 최선은 아니라는 것도 확인했다. K-Sum Pairs는 짝이 `k - x`로 결정되기 때문에 카운터 한 번이면 정렬조차 필요 없었다. 다음에는 투 포인터를 떠올렸을 때 "정렬 비용을 감수할 만한가, 아니면 해시로 짝을 바로 찾을 수 있는 문제인가"를 먼저 한 번 따져보려고 한다.
