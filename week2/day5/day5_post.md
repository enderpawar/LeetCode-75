# [LeetCode 75 Day 12] 238. Product of Array Except Self & 334. Increasing Triplet Subsequence

이번 회차에 푼 두 문제는 겉보기 유형이 전혀 다르다. 하나는 곱셈 배열을 만드는 문제고, 다른 하나는 증가하는 세 수가 있는지 판별하는 문제다. 그런데 막상 풀고 나니 두 문제가 정확히 같은 지점에서 막혔다. 둘 다 "직관대로 짜면 이중, 삼중 반복문이 되고, 그러면 시간 초과"라는 벽이었다.

두 문제 모두 처음 떠오른 풀이는 기각됐고, 결국 반복문을 겹치는 대신 **바깥에 값을 몇 개 들고 다니면서 한 번만 훑는** 형태로 바뀌었다. 그 전환 과정을 남겨두려고 한다.

## 1. 238. Product of Array Except Self - 자신을 제외한 나머지의 곱

정수 배열 `nums`가 주어질 때, `answer[i]`가 `nums[i]`를 제외한 나머지 모든 원소의 곱이 되도록 배열을 만들어 반환한다. 조건이 까다로운데, **시간 복잡도 `O(n)`**에 **나눗셈 연산 금지**다.

```python
class Solution(object):
    def productExceptSelf(self, nums):
        """
        :type nums: List[int]
        :rtype: List[int]
        """
        n = len(nums)
        answer = [1] * n

        left = 1
        for i in range(n):
            answer[i] = left   # 지금까지 누적된 값 = i의 왼쪽 전체 곱
            left *= nums[i]

        right = 1
        for j in range(n - 1, -1, -1):   # 역순회
            answer[j] *= right
            right *= nums[j]

        return answer
```

처음에 떠오른 건 전체 곱을 구해놓고 `nums[i]`로 나누는 방법이었다. 이건 문제가 나눗셈을 금지해서 바로 막혔다. 그다음엔 `i`마다 나머지를 전부 곱하는 이중 반복문을 생각했는데, `nums.length`가 최대 `10^5`이라 `O(n^2)`은 그대로 시간 초과다.

돌파구는 "`i`를 제외한 곱"을 **`i`의 왼쪽 전체 곱 × `i`의 오른쪽 전체 곱**으로 쪼갠 것이었다. 이렇게 보면 `i`마다 나머지를 다시 훑을 필요가 없다. 왼쪽 곱은 앞에서부터 한 번, 오른쪽 곱은 뒤에서부터 한 번 누적하면 끝난다.

코드를 실행 순서대로 보면 이렇다. 첫 번째 반복문에서 `left`는 "아직 `nums[i]`를 곱하지 않은 상태"의 누적값이다. 그래서 `answer[i] = left`를 **먼저** 대입한 뒤에 `left *= nums[i]`를 해야 한다. 순서를 바꾸면 자기 자신까지 곱해져버린다. 이 시점에서 `answer`는 각 칸에 왼쪽 곱만 들어 있는 상태다.

두 번째 반복문은 `range(n - 1, -1, -1)`로 뒤에서 앞으로 간다. 세 번째 인자 `-1`이 step이고, 두 번째 인자 `-1`은 "인덱스 0까지 포함하려면 그보다 하나 더 가야 한다"는 의미라서 `0`이 아니라 `-1`이다. 여기서도 `answer[j] *= right`를 먼저 하고 `right *= nums[j]`를 나중에 한다. 이미 왼쪽 곱이 들어 있는 칸에 오른쪽 곱을 곱해주니까 한 번의 대입으로 최종값이 완성된다.

`[1,2,3,4]`로 확인하면, 첫 반복 뒤 `answer`는 `[1, 1, 2, 6]`이 된다. 역순회하면서 차례로 `6*1=6`, `2*4=8`, `1*12=12`, `1*24=24`가 되어 `[24,12,8,6]`이 나온다.

0이 섞인 `[-1,1,0,-3,3]`도 따로 분기하지 않고 그냥 통과한다. 왼쪽 곱이 `[1,-1,-1,0,0]`이고 오른쪽 곱을 곱하면 `[0,0,9,0,0]`이 된다. 0이 있는 자리는 그 0을 자기 자신으로 빼고 계산하니까 9가 남고, 나머지 자리는 어느 한쪽 곱에 0이 끼어 있어 자동으로 0이 된다. 나눗셈 풀이였다면 여기서 `ZeroDivisionError`를 따로 처리해야 했을 텐데, 누적곱 방식은 0을 특별 취급하지 않아도 된다는 게 마음에 들었다.

풀면서 걸렸던 부분은 다음과 같았다.

- 나눗셈 금지 조건을 "그냥 제약 하나 붙었네" 정도로 봤는데, 사실은 접근 방향을 바꾸라는 지시였다. `-30 ~ 30` 범위를 훑으면서 큰 수를 나눠보려는 시도도 해봤지만 전부 같은 벽에 부딪혔다.
- 대입과 누적의 순서. `answer[i] = left`와 `left *= nums[i]`를 반대로 쓰면 자기 자신이 포함돼서 답이 완전히 어긋난다. 두 반복문 모두 "먼저 쓰고, 그다음 누적"이라는 같은 리듬이라는 걸 알고 나서 외우기 쉬워졌다.
- `range(n - 1, -1, -1)`의 가운데 `-1`. 처음엔 `range(n - 1, 0, -1)`로 써서 인덱스 0을 통째로 빼먹었다.

시간 복잡도는 `O(n)`이다. 반복문이 두 개지만 중첩이 아니라 나란히 있어서 `2n`, 즉 `O(n)`이다. 공간 복잡도는 반환 배열을 제외하면 `O(1)`이다.

## 2. 334. Increasing Triplet Subsequence - 증가하는 세 수 찾기

`i < j < k`이면서 `nums[i] < nums[j] < nums[k]`인 인덱스 세 쌍이 존재하면 `True`, 없으면 `False`를 반환한다. 연속된 세 수일 필요는 없고 순서만 유지되면 된다.

```python
class Solution(object):
    def increasingTriplet(self, nums):
        """
        :type nums: List[int]
        :rtype: bool
        """
        first = float("inf")
        second = float("inf")

        for num in nums:
            if num <= first:
                first = num
            elif num <= second:
                second = num
            else:
                # first < second < num 이 성립하고,
                # 등장 순서상 인덱스 조건도 이미 만족한다
                return True

        return False
```

이 문제는 기각한 풀이가 더 많았다.

가장 먼저 생각한 건 최솟값을 찾고 그다음 최솟값을 찾는 방식이었는데, 가장 작은 값이 배열 맨 뒤에 있으면 그 뒤로 두 수를 더 찾을 수 없어서 성립하지 않는다. 다음으로 앞에서부터 순차적으로 조건을 만족하는 값을 이어붙이는 방식을 시도했다가 `[1,5,0,4,1,3]`에서 막혔다. 마지막엔 삼중 반복문으로 정직하게 다 확인해봤는데 이건 `O(n^3)`이라 당연히 시간 초과가 났다.

정답은 값 두 개만 들고 순회하는 것이었다. `first`는 지금까지 본 가장 작은 값, `second`는 "앞에 자기보다 작은 값이 최소 하나 존재하는" 값 중 가장 작은 값이다. 두 번째 정의가 이 풀이의 핵심이다. `second`에 값이 들어갔다는 것 자체가 "그보다 작은 수가 이미 앞에 나왔다"는 증거이기 때문에, 이후에 `second`보다 큰 수를 만나는 순간 세 쌍이 완성된다.

여기서 한동안 헷갈렸던 건 인덱스였다. `first`가 나중에 더 작은 값으로 갱신되면 `first`의 인덱스가 `second`의 인덱스보다 뒤로 갈 수도 있다. 그러면 `i < j < k`가 깨지는 것 아닌가 싶었는데, 그렇지 않다. `second`가 갱신될 당시에 이미 그보다 작은 값이 앞에 있었다는 사실은 사라지지 않는다. 나중에 `first`가 더 작은 값으로 바뀌어도 판정에는 영향을 주지 않고, 오히려 앞으로 세 쌍을 만들 여지를 넓혀줄 뿐이다.

앞에서 막혔던 `[1,5,0,4,1,3]`을 이 코드로 따라가면 이렇게 흘러간다.

```
1 -> first = 1
5 -> second = 5
0 -> first = 0        (5보다 작은 1이 앞에 있었다는 사실은 second에 남아 있음)
4 -> second = 4
1 -> second = 1
3 -> first(0) < second(1) < 3  -> True
```

`first`가 0으로 내려가고 `second`가 1까지 내려갔지만, 실제 정답이 되는 세 쌍은 `(0, 1, 3)` 즉 인덱스 `(2, 4, 5)`다. 값만 비교했는데 인덱스 순서가 저절로 맞는 이유는, 순회 자체가 인덱스 증가 순서이기 때문이다. 노트에 "어차피 인덱스는 순차적으로 증가해서 비교 필요 x, 값만"이라고 적었던 게 이 얘기였다.

풀면서 걸렸던 부분은 다음과 같았다.

- 비교 연산자를 `<`가 아니라 `<=`로 써야 한다. 문제는 **엄격하게 증가**하는 세 수를 요구하는데, `<`로 쓰면 `[1,1,1]` 같은 입력에서 `first = 1`, `second = 1`이 되고 세 번째 1이 `else`로 빠져 `True`를 반환해버린다. 같은 값은 갱신 쪽으로 흘려보내야 한다.
- 초기값을 0이나 `nums[0]`으로 두려다가 음수 입력에서 어긋났다. `float("inf")`를 쓰면 어떤 정수보다도 커서 첫 두 값이 자연스럽게 `first`, `second`에 자리를 잡는다.
- 삼중 반복문을 짤 때 `return True`가 안쪽에서 제대로 빠져나오는지 확인하려고 `print`를 박아뒀는데, 로직이 맞아도 시간 초과면 소용없다는 걸 그때 체감했다.

시간 복잡도는 `O(n)`, 공간 복잡도는 `O(1)`이다.

## 3. Follow-up 조건에 대한 고찰

두 문제 모두 아래에 follow-up이 달려 있었다.

> **238.** Can you solve the problem in `O(1)` extra space complexity? (The output array does not count as extra space for space complexity analysis.)
>
> **334.** Could you implement a solution that runs in `O(n)` time complexity and `O(1)` space complexity?

처음엔 이걸 "여유 되면 도전해보라"는 보너스 정도로 읽었다. 그런데 정리하고 보니 순서가 반대였다. 두 문제에서 내가 최종적으로 도달한 풀이가 곧 follow-up의 답이었다. follow-up은 추가 과제가 아니라 **정답 풀이의 형태를 미리 알려주는 힌트**였던 셈이다.

### 238번 - "출력 배열은 빼준다"는 단서를 왜 굳이 붙였을까

괄호 안의 문장이 인심을 쓰는 것처럼 보이지만, 사실은 없으면 문제가 성립하지 않는 조건이다. 길이 `n`짜리 배열을 반환해야 하는 이상 `O(n)`만큼의 메모리는 무조건 쓰게 되어 있다. 그걸 계산에 넣으면 `O(1)`은 달성 가능한 목표가 아니라 애초에 모순이다. 즉 이 단서는 "반환용 배열 말고, **보조 배열**을 없앨 수 있느냐"로 질문을 좁혀준 것이다.

이렇게 읽고 나면 중간 단계가 뭐였는지가 분명해진다. 누적곱 아이디어를 처음 떠올렸을 때 자연스럽게 나오는 코드는 배열 두 개를 만드는 형태다.

```python
# follow-up을 만족하지 못하는 중간 단계
left = [1] * n
right = [1] * n

for i in range(1, n):
    left[i] = left[i - 1] * nums[i - 1]

for j in range(n - 2, -1, -1):
    right[j] = right[j + 1] * nums[j + 1]

return [left[i] * right[i] for i in range(n)]
```

이건 시간은 `O(n)`으로 이미 문제 조건을 만족하지만 공간이 `O(n)`이다. 여기서 배열 두 개를 어떻게 지우느냐가 follow-up의 전부다.

지우는 순서가 있다. `left`는 어차피 `answer`에 담아야 할 값과 크기가 같으니 **출력 배열에 그대로 써버리면** 공짜다. 남는 건 `right` 하나인데, 여기서 핵심 질문은 "왜 `right`만 스칼라로 접히는가"이다. 최종값을 계산하려면 `left[i]`와 `right[i]`가 **동시에** 필요한데, `left`는 이미 `answer[i]`에 들어 있으니 `right[i]`는 그 한 순간에만 존재하면 된다. 그리고 역방향 순회는 `right[i]`를 만드는 순서와 소비하는 순서가 정확히 일치한다. 만들자마자 쓰고 버리니 저장할 이유가 없다.

이건 방향에 대해 대칭이라는 점도 재미있다. 오른쪽 곱을 먼저 `answer`에 채우고 정방향으로 `left` 스칼라를 굴려도 똑같이 동작한다. 두 방향 중 **하나는 반드시 실체화해야 하는데, 그 자리를 출력 배열이 공짜로 대주는 구조**다. 그래서 이 문제의 `O(1)`은 "메모리를 아꼈다"기보다 "이미 내야 하는 비용에 계산을 얹었다"에 가깝다.

### 334번 - 여기서는 `O(n)` 시간부터가 조건이다

238번은 본문에서 이미 `O(n)` 시간을 요구했기 때문에 follow-up이 공간만 물었다. 반면 334번은 시간과 공간을 함께 묶어서 물어본다. 이건 "시간만 `O(n)`으로 맞추는 건 상대적으로 쉽다"는 뜻으로 읽어도 된다. 실제로 그렇다.

각 위치 `j`를 가운데 원소라고 가정하면, 필요한 건 두 가지다. 앞쪽에 `nums[j]`보다 작은 값이 하나라도 있는가, 뒤쪽에 `nums[j]`보다 큰 값이 하나라도 있는가. 그러니 앞에서부터의 최솟값 배열과 뒤에서부터의 최댓값 배열을 미리 만들어두면 끝난다.

```python
# 시간은 O(n)이지만 공간이 O(n)이라 follow-up 미달
min_left = [0] * n
max_right = [0] * n

min_left[0] = nums[0]
for i in range(1, n):
    min_left[i] = min(min_left[i - 1], nums[i])

max_right[n - 1] = nums[n - 1]
for i in range(n - 2, -1, -1):
    max_right[i] = max(max_right[i + 1], nums[i])

for j in range(1, n - 1):
    if min_left[j - 1] < nums[j] < max_right[j + 1]:
        return True
return False
```

238번과 구조가 똑같다는 게 눈에 띈다. 앞에서 한 번, 뒤에서 한 번 훑어서 배열 두 개를 만들고 마지막에 합치는 형태다. 그래서 follow-up이 요구하는 것도 같다. 이 두 배열을 스칼라로 접을 수 있느냐.

`min_left`는 쉽다. 정방향 순회에서 변수 하나로 갱신하면 그만이고, 그게 `first`다. 문제는 `max_right`다. 이건 **미래의 정보**라서 정방향 순회로는 만들 수가 없다. 238번에서는 역방향으로 한 번 더 돌면 됐지만, 여기서는 판정에 두 값이 동시에 필요해서 방향을 나눠 도는 것만으로는 해결되지 않는다.

그래서 최종 풀이는 질문 자체를 뒤집는다. "뒤에 더 큰 수가 있는가"를 지금 확인하려 들지 말고, **미래의 원소가 도착했을 때 스스로 판정하게** 만드는 것이다. 그러려면 과거를 요약해서 들고 있어야 하는데, 그 요약이 `second`다. `second`에 값이 들어갔다는 건 "이 값보다 작은 수가 앞에 이미 나왔다"는 사실이 저장됐다는 뜻이고, 그러면 나중에 `second`보다 큰 값을 만나는 원소가 알아서 `True`를 외칠 수 있다. `max_right` 배열이 하던 일을 배열 없이 처리하는 방법이 이거였다.

이렇게 보면 `first`/`second` 풀이는 갑자기 튀어나온 묘수가 아니라 위 두 배열 풀이의 압축본이다. `first`는 `min_left`를 그대로 접은 것이고, `second`는 `max_right`를 접는 대신 판정 시점을 미래로 미룬 것이다. 앞에서 한참 헷갈렸던 "`first`의 인덱스가 `second`보다 뒤로 가도 되나" 하는 의문도, `second`가 값이 아니라 **이미 성립한 사실의 기록**이라는 걸 알고 나면 자연스럽게 풀린다.

또 하나, 334번은 238번과 달리 반환값이 `bool` 하나라서 출력 배열 예외 같은 게 없다. 여기서의 `O(1)`은 문자 그대로 변수 두 개다.

### 두 문제에서 공통으로 남은 규칙

`O(1)` 공간 follow-up이 붙어 있으면, 대체로 "보조 테이블을 스칼라로 접을 수 있는가"를 묻는 것이라고 봐도 될 것 같다. 접히려면 두 조건이 필요하다. 첫째, 저장하려는 값이 **증분으로 갱신 가능한 누적량**이어야 한다. 곱이나 최솟값처럼 앞의 결과에 새 원소 하나만 결합하면 되는 종류여야 한다는 뜻이다. 둘째, 그 값을 **만드는 순서와 쓰는 순서가 같은 방향**이어야 한다.

238번은 첫째 조건은 만족하는데 둘째가 한쪽에서 어긋난다. 왼쪽 곱과 오른쪽 곱이 서로 반대 방향이라 한 방향 순회로는 둘을 동시에 맞출 수 없다. 그래서 한쪽을 출력 배열에 실체화하는 것으로 우회했다. 334번은 둘째 조건이 더 크게 어긋나서, 아예 질문을 뒤집어 판정을 미래에 넘기는 방식으로 풀었다.

거꾸로 이 조건이 깨지면 `O(1)`이 안 되는 것도 짐작이 간다. 만약 각 위치에서 "앞쪽 원소들 중 세 번째로 작은 값" 같은 게 필요했다면 스칼라 하나로는 절대 요약이 안 되고, 그때는 `O(n)` 공간이 진짜로 필요한 비용이 된다. follow-up이 `O(1)`을 걸어준다는 것 자체가 "요약 가능한 문제"라는 보증이기도 한 셈이다.

## 4. 스스로 묻고 답한 질문들

### Q. 238번에서 0의 개수를 세는 풀이도 있던데, 그게 더 쉬운 것 아닌가?

0이 두 개 이상이면 전부 0, 하나면 그 자리만 나머지 곱, 없으면 전체 곱을 나누는 방식인데 이건 나눗셈을 쓰기 때문에 이 문제 조건에서는 애초에 쓸 수 없다. 조건이 없더라도 0의 개수에 따라 분기를 세 갈래로 나눠야 해서 코드가 더 길어진다. 누적곱 방식은 분기 자체가 없다.

### Q. 334번을 `first`, `second`, `third` 세 변수로 확장하면 길이 4짜리 증가 수열도 판별할 수 있나?

같은 형태로 확장은 되지만 일반적으로 안전한 방법은 아니다. 길이가 커질수록 "앞에 더 작은 값이 있었다"는 근거를 변수 하나에 압축하는 논리가 유지되는지 매번 따져야 한다. 임의 길이 `k`로 일반화하려면 최장 증가 부분 수열(LIS) 문제로 접근해서 이분 탐색을 쓰는 `O(n log n)` 풀이로 가는 게 정석이다. 세 개짜리는 그 LIS 풀이의 아주 작은 특수 케이스라고 볼 수 있다.

### Q. `float("inf")` 말고 다른 초기값은 없나?

문제에서 값 범위를 명시했다면 그보다 확실히 큰 상수를 써도 된다. 다만 범위를 잘못 기억하면 바로 틀리기 때문에 `float("inf")`가 더 안전하다. 파이썬에서는 정수와 `float("inf")` 비교가 문제없이 동작하고, 반환값이 `bool`이라 실수형이 섞이는 것도 신경 쓸 필요가 없다.

### Q. 두 문제에서 반복문을 두 번 도는 것과 한 번 안에서 다 처리하는 것 중 어느 쪽이 나은가?

복잡도만 보면 같다. 238번은 왼쪽과 오른쪽이 서로 반대 방향이라 한 번에 처리하려면 양쪽 포인터를 동시에 굴려야 하는데, 코드가 짧아지는 대신 읽기가 어려워진다. `O(2n)`과 `O(n)`은 같은 등급이니, 중첩만 아니라면 반복문을 나누는 쪽이 낫다고 판단했다. 중요한 건 반복문의 개수가 아니라 **겹치는지 여부**다.

## 정리하며

이번 회차에서 확실해진 건 `O(n^2)`가 보일 때 빠져나오는 방향이 대체로 정해져 있다는 점이다. 안쪽 반복문이 하는 일을 **바깥에 들고 다니는 값 몇 개로 대체할 수 있는가**를 먼저 물어보면 된다. 238번에서는 그 값이 누적곱 `left`, `right`였고, 334번에서는 `first`, `second`였다.

접근 방식도 조금 바뀌었다. 예전에는 반례를 만나면 조건문을 덧붙여서 막으려 했는데, 이번엔 `[1,5,0,4,1,3]`에서 막혔을 때 조건을 추가하는 대신 "내가 무엇을 기억하고 있어야 하는가"를 다시 정의했더니 코드가 오히려 짧아졌다. 반례는 코드를 고치라는 신호가 아니라 상태 정의를 고치라는 신호일 때가 많은 것 같다.

그리고 앞으로는 follow-up을 먼저 읽어야겠다고 생각했다. 이번 두 문제 다 follow-up이 요구하는 `O(1)` 공간이 곧 정답 풀이의 모양이었는데, 나는 그걸 다 풀고 나서야 확인했다. 제약 조건은 답을 막는 장애물이 아니라 답의 형태를 좁혀주는 정보에 가깝다.
