# [LeetCode 75 Day 19] 443. String Compression

Day 16~18은 스택 위주로 붙어 있다가, 오늘은 배열을 직접 훑으면서 제자리에서(in-place) 값을 갱신하는 두 포인터 문제로 넘어왔다. 의사코드 단계에서부터 "별도 리스트에 저장하는 건 O(1) 공간복잡도 조건에 걸리니 기각, 포인터로 해야 한다"까지는 바로 잡았는데, 그다음이 문제였다. 그룹 길이가 두 자리 수 이상이면 어떻게 나눠 넣어야 하는지 감이 안 잡혔고, 그 불안이 그대로 구현 버그로 이어졌다.

## 1. String Compression - 읽기/쓰기 포인터로 배열을 직접 압축하기

문자 배열 `chars`가 주어지면, 연속으로 반복되는 문자 그룹을 "문자 + 그룹 길이(길이가 1이면 숫자 생략)" 형태로 압축해서 같은 배열에 덮어써야 한다. 별도의 배열을 쓰지 않고 O(1) 추가 공간으로 풀어야 한다.

```python
class Solution:
    def compress(self, chars):
        write = 0
        read = 0

        while read < len(chars):
            crt_char = chars[read]
            char_cnt = 0

            # 같은 문자가 이어지는 동안 read를 끝까지 밀어붙임
            while read < len(chars) and chars[read] == crt_char:
                read += 1
                char_cnt += 1

            # 문자 먼저 쓰고 포인터 증가
            chars[write] = crt_char
            write += 1

            # 길이가 2 이상일 때만 자릿수별로 기록
            if char_cnt > 1:
                for digit in str(char_cnt):
                    chars[write] = digit
                    write += 1

        return write
```

`read`와 `write` 두 포인터를 쓰되, 역할을 완전히 나눴다. `read`는 안쪽 `while`에서 같은 문자가 이어지는 한 끝까지 먼저 다 밀고 나가서 그룹 하나(`crt_char`, `char_cnt`)를 통째로 확정짓는다. 그 다음에야 `write`가 움직여서 확정된 그룹을 기록한다. "한 그룹을 완전히 다 읽은 다음에 쓴다"는 순서가 이 풀이의 핵심인데, 이렇게 하면 `write`가 항상 `read`보다 뒤에 머무는 게 자연스럽게 보장된다. 그룹 길이가 얼마든 문자 1개 + 숫자 자릿수만큼만 쓰는데, 숫자 자릿수는 그 그룹의 실제 길이보다 항상 작거나 같기 때문이다.

`char_cnt > 1`일 때만 숫자를 붙이는 것도 문제 조건 그대로다. 자릿수를 나누는 부분은 `char_cnt // 10`이나 `% 10` 같은 계산 없이 `str(char_cnt)`로 문자열로 바꾼 다음 한 글자씩 순회하면 끝난다. `for digit in str(12)`는 `"1"`, `"2"`를 순서 그대로 내주기 때문에, 몇 자리 수든 신경 쓸 필요가 없다.

풀면서 걸렸던 부분은 다음과 같았다.

- **처음엔 `crt_char`를 갱신하는 코드 자체가 없었다.** `crt_char = ' '`로 시작만 해두고 어디서도 다시 대입하지 않아서, `chars[read] != crt_char` 조건이 매번 참이 되어버렸다. 결과적으로 모든 반복이 "새 그룹 발견" 분기로 빠지고, `read`는 1씩 늘어나는데 `write`는 그보다 빠르게 늘어나면서 `IndexError`가 났다.
- **`crt_char`는 고쳤는데 정작 문자 자체를 배열에 쓰는 코드가 없었다.** 숫자만 계속 써넣다 보니 아직 `read`가 읽지도 않은 칸이 먼저 덮어써졌고, 그 오염된 값을 다음 반복에서 진짜 데이터인 것처럼 읽어서 없던 그룹이 계속 생겨났다.
- **카운트가 0이어도 무조건 숫자를 쓰고 있었다.** 처음 `crt_char`가 `' '`인 상태를 "카운트 0짜리 그룹"으로 오인해서 불필요한 숫자를 써버렸다. `char_cnt > 1`처럼 실제로 숫자가 필요한 경우만 걸러내는 조건이 빠져 있으면, 배열을 다 읽기도 전에 쓰기 포인터가 앞질러 나가는 문제가 형태만 바뀐 채 계속 반복됐다.
- **자릿수를 나누는 계산에서 `^`을 거듭제곱으로 착각했다.** `char_cnt // 10 ^ (digits - 1)`이라고 썼는데, 파이썬에서 `^`는 XOR 연산자이지 거듭제곱이 아니다(거듭제곱은 `**`). 게다가 `//`가 `^`보다 우선순위가 높아서 계산 순서도 의도와 달랐다. 자릿수를 직접 계산하려 한 게 문제였고, `str()`로 바꿔서 순회하는 쪽이 훨씬 간단하다는 걸 여기서 알게 됐다.

시간 복잡도는 `O(n)`, 공간 복잡도는 입력 배열을 그대로 재사용하므로 `O(1)`이다.

### 더 개선한다면

시간·공간 복잡도는 이미 최적이라 더 줄일 곳은 없다. 대신 "연속된 같은 문자를 묶어서 세는" 부분을 직접 두 개의 `while`로 짜는 대신, `itertools.groupby`에게 그대로 맡길 수 있다.

```python
from itertools import groupby

class Solution:
    def compress(self, chars):
        write = 0

        for char, group in groupby(chars):
            char_cnt = sum(1 for _ in group)

            chars[write] = char
            write += 1

            if char_cnt > 1:
                for digit in str(char_cnt):
                    chars[write] = digit
                    write += 1

        return write
```

`groupby(chars)`는 연속된 같은 값을 `(값, 그룹)` 쌍으로 바로 묶어주기 때문에 `crt_char`, 안쪽 `while` 같은 상태 관리가 사라진다. 다만 `groupby`도 내부적으로 그룹 경계를 확인하려고 항상 다음 원소 하나를 미리 읽어두는데, 그 시점이 우리가 `write`로 같은 자리를 되돌아와 덮어쓰는 시점보다 항상 앞서기 때문에 제자리 수정과 같이 써도 안전하다. 시간·공간 복잡도는 `O(n)`/`O(1)`로 동일하지만, `write`가 `read`를 절대 앞지르지 않는다는 보장을 코드에서 직접 눈으로 확인할 수 있던 두 포인터 버전과 달리, 이 안전성이 `groupby` 내부 구현에 맡겨진다는 점은 트레이드오프다.

## 2. 스스로 묻고 답한 질문들

### Q. `write`가 `read`를 절대 앞지르지 않는다는 걸 어떻게 보장하나?

한 그룹을 압축하면 최소 1글자(문자 자체)에서 최대 1 + len(str(그룹 길이))만큼 쓴다. 그룹 길이가 `k`면 숫자 자릿수는 `len(str(k))`인데, 이는 항상 `k`보다 작거나 같다(`k=1`일 땐 숫자를 아예 안 쓰니 1, `k=99`여도 자릿수는 2뿐이다). 반면 `read`는 그 그룹만큼 정확히 `k`번 전진한다. 즉 그룹 하나당 `write`가 늘어나는 양은 `read`가 늘어나는 양보다 항상 작거나 같으므로, 전체적으로 `write <= read`가 깨질 수 없다. 처음 버그들은 전부 이 부등식이 어딘가에서 무너지면서 생긴 것이었다.

### Q. `char_cnt // 10 ^ (digits - 1)`이 왜 틀렸나?

`^`는 파이썬에서 비트 단위 XOR이다. 거듭제곱을 쓰려면 `**`를 써야 한다. 설상가상으로 연산자 우선순위 때문에 `//`가 `^`보다 먼저 계산되어, `(char_cnt // 10) ^ (digits - 1)`로 해석된다. 애초에 자릿수별로 숫자를 떼어내려 한 접근 자체가 복잡했던 것이고, `str(char_cnt)`로 바꿔서 각 글자를 그대로 순회하면 나눗셈이나 나머지 연산 없이 몇 자리 수든 그대로 처리된다.

### Q. 그룹을 다 읽고 나서 쓰는 방식과, 새 문자를 만날 때 이전 그룹을 flush하는 방식은 뭐가 다른가?

의사코드 단계에서는 후자("새로운 문자열 나오면 cnt 초기화")에 가까운 그림을 그렸는데, 이 방식은 "지금 만난 문자"와 "직전 그룹을 기록하는 일"이 같은 반복 안에서 뒤섞인다. 그러다 보니 직전 그룹의 숫자를 쓰는 타이밍이 새 문자를 쓴 다음으로 밀려서 순서가 꼬이기 쉬웠다. 반대로 안쪽 `while`로 그룹을 끝까지 다 확정한 뒤에 쓰는 방식은, "세는 단계"와 "쓰는 단계"가 아예 분리되어 있어서 쓰는 시점엔 그 그룹에 대해 더 이상 확인할 게 없다. 상태를 오래 들고 있지 않아도 된다는 점에서 훨씬 덜 헷갈렸다.

## 정리하며

이번 문제에서 가장 크게 남은 건 "포인터 두 개를 쓴다"는 아이디어 자체는 처음부터 맞았는데, 그 포인터들이 정확히 언제 움직이고 언제 멈춰야 하는지를 느슨하게 짜서 계속 같은 종류의 사고(쓰기 포인터가 읽기 포인터를 앞지르는 것)가 반복됐다는 점이다. `crt_char`를 갱신하는 줄 하나, 실제 문자를 쓰는 줄 하나, 카운트 조건 하나가 차례로 빠져 있었는데 매번 증상은 `IndexError` 하나로 똑같이 나타났다. 앞으로 제자리 수정 문제를 보면 "쓰기 포인터가 읽기 포인터를 넘어설 수 있는가"부터 먼저 따져보게 될 것 같다.
