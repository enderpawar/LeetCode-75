# [LeetCode 75 Day 16] 2390. Removing Stars From a String & 735. Asteroid Collision

Day 16부터는 스택 파트로 넘어왔다. 앞의 해시맵 문제들이 "무엇을 키로 세어둘 것인가"를 정하는 문제였다면, 이번 두 문제는 "지금까지 남아 있는 것들 중 가장 최근 것만 보면 되는가"를 판단하는 문제였다.

두 문제 모두 스택을 쓰지만 요구하는 바는 꽤 달랐다. 앞 문제는 스택의 기본 동작인 `push`와 `pop`을 조건 하나로 나눠 쓰면 끝났고, 뒤 문제는 충돌이 연쇄적으로 일어나서 `pop`을 몇 번 해야 할지가 입력에 따라 달라졌다. 뒷문제를 정리하면서 `while ... else` 구문을 처음으로 의도해서 써봤고, 이 글에서는 그 부분에 무게를 뒀다.

## 1. Removing Stars From a String - 별표로 앞 글자 지우기

소문자와 `*`로 이루어진 문자열 `s`가 주어진다. `*`를 만나면 그 별표 자신과, 그 왼쪽에서 가장 가까이 남아 있는 문자 하나를 함께 지운다. 이 연산을 모든 별표에 대해 수행한 뒤 남은 문자열을 반환하는 문제다. 지울 문자가 항상 존재한다는 것은 문제에서 보장한다.

```python
class Solution(object):
    def removeStars(self, s):
        stack = []

        for char in s:
            if char == '*':
                stack.pop()
            else:
                stack.append(char)

        return ''.join(stack)
```

문제 설명의 "왼쪽에서 가장 가까이 남아 있는 문자"라는 말이 곧 스택이다. 가장 최근에 넣은 것이 가장 먼저 나오는 구조이고, 이미 지워진 문자는 스택에 없으니 "남아 있는" 것들 중에서만 고른다는 조건도 저절로 지켜진다. 그래서 별표를 만나면 `pop`, 그 외의 문자는 `append` 두 줄이면 끝난다.

`leet**cod*e`를 따라가보면 이렇게 된다. `l`, `e`, `e`, `t`가 쌓여서 `['l','e','e','t']`가 되고, 첫 번째 별표가 `t`를, 두 번째 별표가 그다음으로 최근인 `e`를 지워서 `['l','e']`가 된다. 이어서 `c`, `o`, `d`가 쌓이고 별표가 `d`를 지운 뒤 `e`가 들어와 `['l','e','c','o','e']`, 즉 `lecoe`가 답이다.

마지막 `''.join(stack)`은 문자 하나씩 담긴 리스트를 하나의 문자열로 합친다. 스택을 문자열로 두고 `result += char`처럼 이어붙이지 않은 이유는, 파이썬 문자열이 불변이라 `+=`가 매번 새 문자열을 만들기 때문이다. 그렇게 하면 전체가 `O(n^2)`이 될 수 있지만, 리스트에 모아뒀다가 마지막에 한 번 `join`하면 `O(n)`으로 끝난다.

풀면서 확인한 점은 다음과 같았다.

- 문자열 자체를 잘라내며 처리하려고 하면 매번 새 문자열이 생겨서 비효율적이고, 인덱스도 계속 어긋난다. 리스트를 스택으로 쓰는 편이 훨씬 단순하다.
- `stack.pop()`은 빈 리스트에서 호출하면 `IndexError`를 낸다. 이 문제는 지울 문자가 항상 있다고 보장해줘서 그냥 써도 되지만, 그 보장이 없었다면 `if stack:` 검사가 필요했을 자리다.

시간 복잡도는 `O(n)`, 공간 복잡도는 `O(n)`이다. 각 문자가 스택에 최대 한 번 들어가고 최대 한 번 나온다.

### 더 개선한다면

시간과 공간 모두 이미 `O(n)`이고, 답 자체가 최대 `n` 길이라 공간을 더 줄일 여지는 없다. 그래서 복잡도 대신 관점을 바꿔봤다. 오른쪽에서 왼쪽으로 훑으면 "아직 처리하지 못한 별표가 몇 개 밀려 있는가"만 세어도 같은 답이 나온다. 별표를 만나면 빚이 하나 늘고, 문자를 만났을 때 빚이 남아 있으면 그 문자를 버리며 빚을 하나 갚는 식이다.

```python
class Solution(object):
    def removeStars(self, s):
        """
        :type s: str
        :rtype: str
        """

        result = []
        stars = 0

        for char in reversed(s):
            if char == '*':
                stars += 1

            elif stars:
                stars -= 1

            else:
                result.append(char)

        result.reverse()

        return ''.join(result)
```

복잡도는 그대로 `O(n)`이라 더 빠르지도 작지도 않다. 대신 스택에서 꺼내는 동작이 정수 하나를 더하고 빼는 것으로 바뀌면서, 이 문제가 사실은 "별표 하나가 문자 하나를 상쇄한다"는 상쇄 문제라는 게 드러난다. 예를 들어 별표 하나가 문자를 `k`개 지우는 변형이 나오면 `stars += k`로 바로 대응된다. 치르는 대가는 가독성이다. 뒤에서부터 읽어야 하고 마지막에 `reverse()`로 순서를 되돌려야 해서, 원래 코드의 `pop`과 `append`만큼 의도가 한눈에 보이지는 않는다.

## 2. Asteroid Collision - 소행성 충돌 처리하기

정수 배열 `asteroids`가 주어진다. 각 원소의 절댓값은 소행성의 크기, 부호는 이동 방향이다. 양수면 오른쪽, 음수면 왼쪽으로 움직이고 속도는 모두 같다. 두 소행성이 만나면 작은 쪽이 폭발하고, 크기가 같으면 둘 다 폭발한다. 같은 방향으로 움직이는 소행성끼리는 절대 만나지 않는다. 모든 충돌이 끝난 뒤 남는 소행성 배열을 반환하는 문제다.

```python
class Solution(object):
    def asteroidCollision(self, asteroids):
        """
        :type asteroids: List[int]
        :rtype: List[int]
        """

        stack = []

        for asteroid in asteroids:

            while stack and stack[-1] > 0 and asteroid < 0:
                if stack[-1] < -asteroid:
                    stack.pop()
                    continue

                elif stack[-1] == -asteroid:
                    stack.pop()

                break

            else:
                stack.append(asteroid)

        return stack
```

속도가 모두 같으니 충돌은 딱 한 경우에만 일어난다. 오른쪽으로 가는 소행성이 먼저 있고, 그 뒤에 왼쪽으로 가는 소행성이 오는 경우다. 그래서 조건이 `stack[-1] > 0 and asteroid < 0`이다. 반대로 왼쪽으로 가는 소행성 뒤에 오른쪽으로 가는 소행성이 오면 둘은 서로 멀어지기만 하므로 볼 필요가 없다.

이때 새로 들어온 왼쪽 방향 소행성이 부딪히는 상대는 항상 **가장 최근에 살아남은 오른쪽 방향 소행성**이다. 앞 문제의 "왼쪽에서 가장 가까이 남아 있는 문자"와 정확히 같은 구조다. 그리고 스택에 남아 있는 값들이 곧 최종 답이라서 결과를 담을 리스트를 따로 둘 필요도 없다.

다만 앞 문제와 달리 `pop`을 몇 번 해야 할지가 정해져 있지 않다. 별표는 언제나 문자 하나만 지우지만, 왼쪽으로 가는 큰 소행성은 앞의 소행성을 여러 개 연달아 부술 수 있다. `if`가 아니라 `while`이 필요한 이유가 여기에 있다.

반복문 안쪽은 충돌이 났을 때의 세 갈래를 처리한다. `stack[-1] < -asteroid`면 스택 위쪽 소행성이 더 작으니 폭발시키고(`pop`), `continue`로 다시 while 조건부터 확인한다. 새로 들어온 소행성은 아직 살아 있으니 그 아래 소행성과 또 부딪힐 수 있기 때문이다. `stack[-1] == -asteroid`면 둘 다 폭발하므로 스택에서 하나 빼고 아래의 `break`로 빠져나간다. 두 조건 모두 아니면 스택 위쪽이 더 크다는 뜻이라 새 소행성만 사라지고, 역시 `break`로 끝난다.

여기서 이 코드의 축은 `while`에 붙은 `else`다. 파이썬의 반복문 `else`는 조건이 참일 때 실행되는 게 아니라, **`break` 없이 반복문이 끝났을 때** 실행된다. 그러니 `else`에 도달하는 경우는 두 가지다. 애초에 충돌 조건이 거짓이라 while을 한 번도 돌지 않은 경우, 그리고 앞을 계속 부수다가 스택이 비었거나 스택 위가 더 이상 오른쪽 방향이 아니게 되어 조건이 거짓이 된 경우다. 두 경우 모두 "이 소행성은 살아남았다"를 뜻하므로 `stack.append(asteroid)`가 정확히 맞는 자리에 온다. 반대로 자기가 폭발한 두 경우에는 `break`로 나왔으므로 `else`가 건너뛰어지고 append도 일어나지 않는다.

경계도 이 구조 덕분에 자연스럽게 처리된다. `[-2, -1, 1, 2]`처럼 충돌이 아예 없는 입력은 while 조건이 매번 거짓이라 전부 append되고, `[1, -1, -2, -2]`는 `-1`이 `1`과 같이 터진 뒤 남은 `-2` 두 개가 빈 스택 위에 그냥 쌓여 `[-2, -2]`가 된다.

풀면서 걸렸던 부분은 다음과 같았다.

- 충돌 조건을 "부호가 다르면"으로 잡으면 틀린다. `-2` 다음에 `2`가 오는 경우는 서로 멀어지는 상황이라 충돌이 아니다. 방향까지 따져서 `stack[-1] > 0 and asteroid < 0`이어야 한다.
- 충돌이 한 번으로 끝나지 않는다는 점. `[10, 2, -5]`에서 `-5`는 `2`를 부수고 나서 `10`과 다시 만난다. `pop` 뒤에 `continue`로 while 조건을 다시 확인하지 않으면 이 연쇄가 끊긴다.
- 살아남은 소행성을 append하는 자리를 어디로 둘지. 조건 분기마다 append를 넣으면 중복이 생기는데, `while ... else`가 "폭발하지 않고 반복문을 빠져나온 경우"를 한 군데로 모아준다.

시간 복잡도는 `O(n)`, 공간 복잡도는 `O(n)`이다. 반복문이 겹쳐 있어 `O(n^2)`처럼 보이지만, 각 소행성은 스택에 최대 한 번 들어가고 최대 한 번 빠져나오므로 `pop` 총 횟수가 `n`을 넘지 않는다.

### 더 개선한다면

시간 복잡도는 모든 원소를 한 번씩은 봐야 하므로 `O(n)`이 하한이고, 이미 거기에 닿아 있다. 다만 공간은 앞 문제와 사정이 다르다. 앞 문제는 입력이 문자열이라 손댈 수 없었지만, 이번에는 입력이 리스트이고 스택에 쌓이는 원소 개수는 언제나 지금까지 읽은 원소 개수 이하다. 즉 이미 읽고 지나온 자리에 덮어쓰면 되므로, 입력 리스트 자체를 스택으로 재사용할 수 있다.

```python
class Solution(object):
    def asteroidCollision(self, asteroids):
        """
        :type asteroids: List[int]
        :rtype: List[int]
        """

        top = 0  # 스택에 살아남은 원소 개수

        for asteroid in asteroids:

            while top > 0 and asteroids[top - 1] > 0 and asteroid < 0:
                if asteroids[top - 1] < -asteroid:
                    top -= 1
                    continue

                elif asteroids[top - 1] == -asteroid:
                    top -= 1

                break

            else:
                asteroids[top] = asteroid
                top += 1

        del asteroids[top:]

        return asteroids
```

`stack[-1]`이 `asteroids[top - 1]`로, `pop()`이 `top -= 1`로, `append`가 `asteroids[top] = asteroid` 뒤 `top += 1`로 바뀐 것뿐이라 판단 논리는 그대로다. 마지막에 `del asteroids[top:]`로 뒤에 남은 옛 값들을 잘라내면 앞쪽 `top`개가 곧 답이 된다. 덮어쓰기가 안전한 이유는 `i`번째 원소를 읽는 시점에 `top <= i`이기 때문이고, 아직 읽지 않은 자리를 건드릴 일이 없다. 추가 공간은 `O(1)`로 줄지만 입력 리스트를 훼손하고 인덱스를 직접 관리해야 해서, `pop`과 `append`로 읽히던 의도가 그만큼 흐려진다.

## 3. 스스로 묻고 답한 질문들

### Q. 2390에서 스택을 문자열로 두고 `+=`로 이어붙이면 안 되나?

답은 맞지만 느려진다. 파이썬 문자열은 불변이라 `result += char`는 기존 문자열을 수정하는 게 아니라 매번 길이가 하나 늘어난 새 문자열을 만들어 복사한다. 그래서 전체가 `O(n^2)`이 될 수 있다. 반대로 리스트의 `append`는 평균 `O(1)`이고 마지막 `join` 한 번이 `O(n)`이라, 리스트에 모았다가 합치는 쪽이 이 문제의 표준적인 방식이다. 별표를 만났을 때 `result = result[:-1]`로 잘라내는 것도 같은 이유로 매번 새 문자열을 만든다.

### Q. 735에서 `pop()` 다음의 `continue`를 빼면 어떻게 되나?

`continue`가 없으면 `pop()` 이후 실행이 아래로 흘러 `elif`를 건너뛰고 `break`에 도달한다. 그러면 한 번 부수고 반복문을 나가버리는 데다, `break`로 나왔으니 `else`도 실행되지 않아서 살아남은 소행성이 스택에 들어가지 않는다. `[10, 2, -5]`가 `[10]`이 아니라 잘못된 결과가 되는 자리다. `continue`는 "아직 이 소행성은 살아 있으니 조건부터 다시 보라"는 뜻이다.

### Q. `while ... else` 대신 플래그 변수를 쓰면 안 되나?

된다. `alive = True`를 두고 폭발하는 분기에서 `alive = False`로 바꾼 뒤 반복문 밖에서 `if alive: stack.append(asteroid)`로 써도 결과는 같다. 다만 상태를 담는 변수가 하나 늘고, 분기마다 그 변수를 빼먹지 않고 갱신했는지 확인해야 한다. `while ... else`는 그 판단을 언어의 제어 흐름에 맡기는 방식이라, "`break`로 나갔는가"라는 사실 하나만 정확히 이해하면 변수 없이 같은 일을 한다.

### Q. `abs(asteroid)` 대신 `-asteroid`를 쓴 게 맞나?

이 자리에서는 맞다. `while` 조건에 이미 `asteroid < 0`이 들어 있어서 그 블록 안에서는 `asteroid`가 항상 음수이고, 따라서 `-asteroid`는 그 소행성의 크기다. 다만 조건을 나중에 손대면 이 전제가 깨질 수 있으니, 의도를 드러내는 쪽을 택한다면 `abs(asteroid)`가 더 안전한 표현이긴 하다.

### Q. 두 문제 모두 답을 담을 리스트를 따로 만들지 않았는데, 왜 그래도 되는가?

스택에서 빠지는 원소는 전부 지워지는 것이고 스택에 남는 원소는 전부 살아남는 것이기 때문이다. 게다가 원소는 왼쪽에서 오른쪽 순서로만 들어가므로 스택 안의 순서가 곧 원래 입력에서의 순서다. 문제가 요구하는 최종 상태와 스택의 상태가 정확히 같아서, 마지막에 스택을 그대로(2390은 `join`해서) 반환하면 된다.

### Q. 735는 반복문이 중첩됐는데 왜 `O(n^2)`이 아닌가?

바깥 반복문이 `n`번 돌고 안쪽 `while`이 최악에 `n`번 돌 수 있으니 형태만 보면 그렇게 보인다. 하지만 안쪽 `while`이 한 바퀴 돌 때마다 반드시 `pop`이 한 번 일어나고, 스택에 들어가는 원소는 총 `n`개뿐이다. 그러므로 전체 실행 동안 `pop`은 많아야 `n`번이고, 안쪽 반복의 총합도 `n`을 넘지 않는다. 한 번의 호출이 아니라 전체를 합쳐서 세는 이런 계산 방식을 분할 상환 분석이라고 부른다.

## 정리하며

Day 16의 두 문제는 같은 자료구조를 쓰면서도 요구하는 게 달랐다. 2390은 스택의 기본 동작 그대로 별표마다 `pop`을 한 번씩 하면 끝났고, 735는 `pop`을 몇 번 할지가 크기 비교에 따라 달라져서 `while`과 조건 분기가 필요했다. 두 문제를 나란히 놓고 보니 스택을 꺼내들 기준이 "가장 최근에 남아 있는 것과만 비교하면 되는가"라는 게 분명해졌다.

문법 쪽에서는 `while ... else`가 `break` 여부로 갈린다는 점, `continue`가 연쇄 충돌을 이어준다는 점이 손에 잡혔다. 두 개가 각각 "이 소행성은 끝까지 살아남았는가"와 "아직 더 부딪힐 게 남았는가"를 담당하고 있어서, 조건 분기를 늘리지 않고도 경우를 나눌 수 있었다. 문자열을 조각내며 다루는 대신 리스트에 모았다가 `join`하는 습관, 그리고 반복문이 겹쳤다고 곧바로 `O(n^2)`으로 세지 않고 원소가 스택에 들어가고 나오는 총 횟수로 세는 관점도 함께 정리했다.
