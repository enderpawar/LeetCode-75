# [LeetCode 75 Day 15] 1657. Determine if Two Strings Are Close & 2352. Equal Row and Column Pairs

Day 15에서는 해시맵과 집합을 쓰는 두 문제를 풀었다. 둘 다 딕셔너리를 쓰지만 목적이 달랐다. 하나는 문자별 등장 횟수를 세서 문자 종류와 빈도 구성을 비교하는 문제였고, 다른 하나는 같은 내용의 행이 몇 번 나왔는지를 세서 열과 대조하는 문제였다.

첫 번째 문제는 문제 설명 자체가 잘 이해되지 않아서 시간이 걸렸고, 접근은 맞았는데 제출에서 169개 중 159개만 통과하는 오답을 겪었다. 두 번째 문제는 솔직히 앞 문제를 풀고 나니 지쳐서 직접 구현을 시도하지 않고 코드부터 먼저 확인했다. 그래서 이 글에서 두 문제의 기록 방식이 조금 다르다.

## 1. Determine if Two Strings Are Close - 두 문자열이 가까운지 판별하기

두 문자열에 다음 두 연산을 원하는 만큼 적용해서 한쪽을 다른 쪽으로 만들 수 있으면 `true`를 반환하는 문제다.

1. 문자열 안에 있는 두 문자의 위치를 서로 바꾼다.
2. 문자열에 이미 존재하는 서로 다른 두 문자를 골라, 두 문자의 모든 등장 위치를 통째로 맞바꾼다.

```python
class Solution(object):
    def closeStrings(self, word1, word2):
        """
        :type word1: str
        :type word2: str
        :rtype: bool
        """
        # 길이가 다르면 어떤 연산으로도 같게 만들 수 없음
        if len(word1) != len(word2):
            return False

        count1 = {}
        count2 = {}

        for char in word1:
            count1[char] = count1.get(char, 0) + 1

        for char in word2:
            count2[char] = count2.get(char, 0) + 1

        # 문자열에 존재하는 문자 종류 비교
        if set(count1.keys()) != set(count2.keys()):
            return False

        # 문자별 등장 횟수의 구성 비교
        frequencies1 = sorted(count1.values())
        frequencies2 = sorted(count2.values())

        return frequencies1 == frequencies2
```

### 문제를 이해하는 데 먼저 걸렸다

처음에는 두 번째 연산이 무엇을 허용하는지가 헷갈렸다. 문자를 마음대로 바꿀 수 있다는 뜻처럼 읽혀서, 그러면 아무 문자열이나 다 만들 수 있는 것 아닌가 싶었다.

정리하고 나니 이건 문자를 새로 만드는 연산이 아니라 **이미 있는 두 문자가 담당하던 등장 횟수를 서로 맞바꾸는 연산**이었다. 예를 들어 `"aaabbc"`에서 `a`와 `b`를 교환하면 `"bbbaac"`가 된다. 빈도로 보면 이렇게 바뀐다.

```text
a: 3          a: 2
b: 2    →     b: 3
c: 1          c: 1
```

어떤 문자가 어떤 횟수를 담당하는지는 바뀌지만, 전체 등장 횟수의 구성인 `[1, 2, 3]` 자체는 변하지 않는다. 그리고 첫 번째 연산은 순서만 섞는 것이라 빈도에 아무 영향이 없다. 결국 두 연산을 아무리 써도 바뀌지 않는 것은 **문자 종류의 집합**과 **빈도들의 정렬된 목록** 두 가지였고, 그 두 개만 비교하면 되는 문제였다.

### 내가 떠올린 접근과 파이썬 문법

의사코드에는 "해시맵으로 문자를 키, 등장 횟수를 값으로 기록해서 비교하면 될 듯"이라고 적어뒀다. 방향은 맞았는데 파이썬에서 해시맵을 어떻게 쓰는지를 몰라서 거기서부터 찾아봤다. 파이썬에서는 `dict`가 해시맵 역할을 한다.

```python
count = {}

for char in word:
    count[char] = count.get(char, 0) + 1
```

`count.get(char, 0)`은 `char`가 딕셔너리에 있으면 그 값을 돌려주고, 없으면 기본값 `0`을 돌려준다. 덕분에 `if char in count:` 같은 존재 검사를 따로 쓰지 않고 한 줄로 빈도를 셀 수 있었다. `"cabbba"`를 세면 `{"c": 1, "a": 2, "b": 3}`이 된다.

그리고 만들어진 딕셔너리에서 문자 종류는 `count.keys()`로, 등장 횟수는 `count.values()`로 꺼낸다. 이 문제는 이 둘을 각각 다른 방식으로 비교해야 했다.

**문자 종류는 그대로 같아야 한다.** `word1 = "aabb"`, `word2 = "aacc"`는 빈도 구성이 둘 다 `[2, 2]`로 같지만 `word1`에는 `c`가 아예 없다. 두 번째 연산은 이미 존재하는 문자끼리만 교환할 수 있으므로 없는 문자를 새로 만들 수는 없다. 그래서 `false`다.

**빈도는 정렬해서 비교해야 한다.** `word1 = "cabbba"`(c 1개, a 2개, b 3개)와 `word2 = "abbccc"`(a 1개, b 2개, c 3개)는 같은 문자끼리의 개수는 다 다르지만 값만 모아 정렬하면 둘 다 `[1, 2, 3]`이다. 두 번째 연산으로 각 문자가 담당하는 빈도를 바꿀 수 있으니 이건 가까운 문자열이다. 즉 `count1["a"] == count2["a"]` 같은 비교를 하면 안 되고, 값들의 목록만 비교해야 한다.

### 159/169로 틀린 부분

처음 제출한 코드에서 문자 종류는 이렇게 비교했다.

```python
if count1.keys() != count2.keys():
    return False
```

169개 테스트 중 159개만 통과했고, 실패한 입력은 이거였다.

```text
word1 = "kyq"
word2 = "kqy"
출력: false / 기대: true
```

두 문자열 모두 `k`, `y`, `q`를 하나씩 가지고 있으니 당연히 `true`여야 했다. 원인은 알고리즘이 아니라 내가 제출한 언어였다. LeetCode에서 `Python 3`가 아니라 `Python`(즉 Python 2)을 선택하고 있었는데, Python 2의 `dict.keys()`는 **리스트**를 반환한다. 리스트끼리의 `==`는 순서까지 따지는 비교라서, 키 목록이 이런 식으로 나오면 결과가 갈린다.

```text
count1.keys(): ["k", "y", "q"]
count2.keys(): ["k", "q", "y"]
```

딕셔너리의 키 순서는 내가 넣은 순서도 아니고 정렬된 순서도 아니다. 해시값에 따라 자리가 정해지고, 충돌이 나면 삽입 순서에 따라 배치가 달라질 수 있다. 그래서 같은 키 집합을 담은 두 딕셔너리라도 키 목록의 순서가 다르게 나올 수 있고, 그게 이 입력에서 그대로 드러났다.

수정은 집합으로 감싸는 것이었다.

```python
set(count1.keys()) != set(count2.keys())
```

Python 3였다면 `keys()`가 뷰 객체를 반환하고 뷰끼리의 비교는 집합처럼 동작해서 원래 코드도 통과했을 것이다. 다만 이걸 "Python 2와 3의 차이"로만 외우고 넘어가면 다음에 또 같은 실수를 할 것 같다. 애초에 이 문제에서 내가 확인하고 싶었던 건 "어떤 문자들이 들어 있는가"라는 순서 없는 정보였다. 그러면 순서가 없는 자료형인 `set`으로 비교하는 게 언어 버전과 무관하게 의도에 맞는 코드다. 실행 환경이 우연히 맞춰준 것에 기대지 말고, 비교하려는 대상의 성질에 맞는 자료형을 고르는 게 맞다고 정리했다.

문자열을 각각 한 번씩 훑으므로 시간 복잡도는 `O(n)`이다. `sorted`가 들어가지만 정렬 대상은 최대 26개(소문자 알파벳)라 전체에 영향을 주지 않는다. 딕셔너리에 저장되는 키도 최대 26개이므로 공간 복잡도는 `O(1)`이다.

### 더 개선한다면

빈도를 세는 반복문 두 개는 `collections.Counter`가 그대로 대신해준다. 그리고 문자 종류를 얻으려고 딕셔너리를 거쳐 `keys()`를 꺼낼 필요도 없다. 문자열에 `set()`을 씌우면 곧바로 등장하는 문자들의 집합이 나온다. 이렇게 쓰면 "순서 없는 문자 종류를 비교한다"는 의도가 코드에 더 직접 드러나서, 내가 틀렸던 지점을 애초에 만들지 않게 된다.

```python
from collections import Counter


class Solution(object):
    def closeStrings(self, word1, word2):
        if set(word1) != set(word2):
            return False

        return sorted(Counter(word1).values()) == sorted(Counter(word2).values())
```

길이 비교도 뺐다. 빈도 목록의 합이 곧 문자열의 길이이므로, 정렬한 빈도 목록이 같으면 길이는 자동으로 같기 때문이다. 실제로 `"a"`와 `"aa"`는 문자 종류가 `{a}`로 같지만 빈도 목록이 `[1]`과 `[2]`라서 `false`가 나온다. 시간·공간 복잡도는 그대로 `O(n)`, `O(1)`이고, 대신 길이가 다른 입력을 첫 줄에서 바로 걸러내던 조기 반환이 사라져 항상 두 문자열을 다 세게 된다는 점은 감수해야 한다.

## 2. Equal Row and Column Pairs - 내용이 같은 행과 열의 쌍 개수

`n × n` 정수 행렬에서 내용이 같은 `(행, 열)` 쌍이 몇 개인지 세는 문제다. 값의 구성만 같아서는 안 되고 원소의 순서까지 같아야 한다.

앞 문제를 풀고 나니 집중력이 떨어져서, 이 문제는 직접 코드를 고민하지 않고 Python 2용 풀이를 먼저 받아서 읽었다. 그래서 여기에는 내가 여러 방법을 시도하다 실패한 과정이 없다. 대신 받은 코드에서 내가 몰랐던 문법을 확인하는 쪽으로 정리했다.

```python
class Solution(object):
    def equalPairs(self, grid):
        """
        :type grid: List[List[int]]
        :rtype: int
        """
        row_count = {}
        answer = 0

        # 각 행을 튜플로 변환해 등장 횟수 저장
        for row in grid:
            row_tuple = tuple(row)
            row_count[row_tuple] = row_count.get(row_tuple, 0) + 1

        # 각 열과 동일한 행이 몇 개 있는지 확인
        for column in zip(*grid):
            answer += row_count.get(tuple(column), 0)

        return answer
```

흐름은 이렇다. 먼저 각 행을 튜플로 바꿔 딕셔너리에 넣으면서 같은 내용의 행이 몇 번 나왔는지 센다. 그다음 열을 하나씩 꺼내서, 그 열과 같은 내용의 행이 딕셔너리에 몇 개 저장되어 있는지를 조회해 답에 더한다. 없으면 `get`의 기본값 `0`이 더해지므로 아무 일도 일어나지 않는다.

여기서 개수를 세는 이유가 중요했다. 같은 내용의 행이 두 개 있고 그 내용과 일치하는 열이 하나 있다면, 만들어지는 쌍은 (행 A, 열) 과 (행 B, 열) 로 두 개다. 문제의 두 번째 예제에서 2번 행과 3번 행이 같은 내용이고 둘 다 2번 열과 일치하므로 각각 별도의 쌍으로 세야 한다. 그래서 "있다/없다"가 아니라 등장 횟수를 저장해두고 그만큼 더해야 한다.

### 왜 리스트를 튜플로 바꿔야 하는가

`row_count[row] = 1`처럼 리스트를 그대로 딕셔너리 키로 쓰면 `unhashable type: 'list'` 오류가 난다. 딕셔너리는 키의 해시값으로 저장 위치를 정하는데, 리스트는 내용이 바뀔 수 있는 자료형이라 해시값이 고정되지 않는다. 저장한 뒤에 내용이 바뀌면 원래 자리에서 찾을 수 없게 되므로 아예 키로 쓰지 못하게 막혀 있다.

튜플은 한 번 만들면 내용을 바꿀 수 없어서 해시값이 고정되고, 그래서 키로 쓸 수 있다. 원소의 순서도 그대로 유지되므로 "순서까지 같아야 한다"는 이 문제의 조건과도 잘 맞는다.

```python
row_tuple = tuple(row)   # [3, 2, 1] → (3, 2, 1)
```

### `zip(*grid)`가 열을 만드는 원리

이 코드에서 제일 생소했던 부분이다. `*grid`는 리스트 안의 각 행을 `zip`의 개별 인자로 풀어서 넘긴다. 그러니까 아래 두 코드는 같은 의미다.

```python
zip(*grid)

zip([3, 2, 1],
    [1, 7, 6],
    [2, 7, 7])
```

`zip`은 넘겨받은 여러 시퀀스에서 같은 위치에 있는 원소끼리 묶어준다. 첫 번째 인자들끼리, 두 번째 인자들끼리 묶이는데, 여기서 "각 행의 같은 위치"란 곧 같은 열이다.

```text
(3, 1, 2)   ← 0번 열
(2, 7, 7)   ← 1번 열
(1, 6, 7)   ← 2번 열
```

열을 직접 만들려면 `for j in range(n): [grid[i][j] for i in range(n)]` 같은 이중 반복이 필요한데, `zip(*grid)`는 그걸 한 줄로 처리해준다. Python 2에서 `zip()`은 튜플들의 리스트를 반환하므로 각 `column`은 이미 튜플이다. 코드에 있는 `tuple(column)`은 그래서 실제로는 없어도 동작하지만, 키의 형태를 눈으로 확인할 수 있게 남겨둔 셈이다.

행렬의 모든 칸을 두 번(행을 세면서 한 번, 열을 만들면서 한 번) 확인하므로 시간 복잡도는 `O(n^2)`이다. 딕셔너리에는 최대 `n`개의 서로 다른 행이 들어가고 각 키는 길이 `n`짜리 튜플이므로, 저장되는 원소 기준으로 공간 복잡도도 `O(n^2)`이다.

### 더 개선한다면

행렬의 모든 칸을 최소 한 번은 읽어야 하므로 `O(n^2)`보다 빠른 방법은 없고, 행을 통째로 저장하는 이상 공간도 `O(n^2)`에서 더 줄이기 어렵다. 대신 `get`으로 세고 `answer`에 누적하던 부분은 `Counter`와 `sum`으로 정리할 수 있다.

```python
from collections import Counter


class Solution(object):
    def equalPairs(self, grid):
        row_count = Counter(tuple(row) for row in grid)

        return sum(row_count[column] for column in zip(*grid))
```

`Counter`는 없는 키를 조회해도 `KeyError` 대신 `0`을 돌려주기 때문에 `get(..., 0)`처럼 기본값을 넘기지 않아도 되고, 조회만으로 그 키가 새로 생기지도 않는다. 복잡도는 그대로지만 `answer`라는 누적 변수가 사라져서 "각 열에 대응하는 행 개수를 전부 더한다"는 의도가 한 줄로 읽힌다. 대신 `Counter`가 무엇을 세고 있는지 모르면 세는 과정이 코드에서 보이지 않는다는 점은 감수해야 한다. 참고로 Python 2의 `zip`은 모든 열을 한꺼번에 리스트로 만들어두는데, `itertools.izip`을 쓰면 열을 하나씩 꺼내 쓸 수 있다. 다만 딕셔너리가 이미 `O(n^2)`을 차지하므로 전체 공간 복잡도가 달라지지는 않는다.

## 3. 스스로 묻고 답한 질문들

### Q. Python 3로 제출했다면 `count1.keys() != count2.keys()`도 통과했을까?

통과했을 것이다. Python 3의 `dict.keys()`는 리스트가 아니라 뷰 객체를 반환하고, 뷰끼리의 `==`는 집합처럼 원소 구성만 비교하기 때문에 순서를 따지지 않는다. 하지만 그건 언어가 우연히 내 의도와 맞아떨어진 것이지 코드가 의도를 표현한 건 아니다. 순서가 상관없는 비교라면 `set`으로 감싸는 편이 어느 버전에서든 안전하다.

### Q. 왜 리스트는 딕셔너리 키로 쓸 수 없고 튜플은 되는가?

딕셔너리는 키의 해시값으로 저장 위치를 계산한다. 리스트는 내용을 바꿀 수 있어서 저장한 뒤 값이 달라지면 해시값도 달라지고, 그러면 원래 넣어둔 자리에서 그 키를 다시 찾을 수 없다. 그래서 파이썬은 아예 리스트에 해시값을 부여하지 않고 `unhashable type: 'list'` 오류를 낸다. 튜플은 내용을 바꿀 수 없어 해시값이 평생 고정되므로 키로 쓸 수 있다.

### Q. 1657에서 `set`을 쓰고 2352에서 `tuple`을 쓴 기준은 무엇인가?

비교하려는 정보에 순서가 의미를 가지느냐가 기준이었다. 1657에서 필요한 건 "어떤 문자들이 들어 있는가"라는 구성뿐이고 순서는 상관없으니 `set`이 맞다. 2352에서는 행과 열이 원소 순서까지 같아야 하므로 순서를 유지하는 `tuple`이 맞다. 여기서 `set`을 썼다면 `[2, 7, 7]`과 `[7, 2, 7]`을 같다고 판단해서 틀린다.

### Q. 1657에서 길이 비교는 꼭 필요한가?

없어도 답은 맞는다. 빈도 목록의 합이 곧 문자열 길이라서, 정렬한 빈도 목록이 같으면 길이도 반드시 같기 때문이다. 다만 길이가 다른 입력을 세기도 전에 바로 걸러낼 수 있어서 조기 반환으로서의 값은 있다.

### Q. 2352에서 열도 딕셔너리에 세서 양쪽을 비교하면 안 되나?

그렇게 하면 안 된다. 이 문제는 서로 다른 종류가 몇 개인지가 아니라 (행, 열) 조합의 개수를 세는 문제라서, 같은 내용이 행에 두 번, 열에 세 번 나왔다면 쌍은 여섯 개다. 한쪽만 딕셔너리에 세두고 다른 쪽을 하나씩 조회하면서 저장된 횟수를 더하는 지금 방식이 이 곱셈을 자연스럽게 처리한다.

## 정리하며

Day 15의 두 문제는 모두 딕셔너리를 썼지만 세는 대상이 달랐다. 1657은 문자별 등장 횟수를 세서 문자 종류와 빈도 구성을 비교했고, 2352는 같은 내용의 행이 몇 번 나왔는지를 세서 각 열과 일치하는 행의 개수를 누적했다. 두 경우 다 "무엇을 키로 삼을 것인가"를 정하는 게 풀이의 절반이었다.

1657은 접근 자체는 처음부터 맞았고 159/169라는 결과도 그걸 보여줬지만, 자료형과 순서 처리에서 틀렸다. 예제만 통과했다고 끝내지 말고 순서가 뒤집힌 입력 같은 것도 한 번 생각해봐야 한다는 걸 확인했다. 2352는 내가 직접 짜지 않고 코드를 먼저 봤으니, 최소한 리스트와 튜플의 차이, 해시 가능성, `zip(*grid)`가 열을 만드는 원리는 다음에 비슷한 문제가 나왔을 때 스스로 떠올릴 수 있도록 남겨둔다.
