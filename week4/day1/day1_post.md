# [LeetCode 75 Day 22] 1161. Maximum Level Sum of a Binary Tree

Day 22에서는 이진 트리의 각 레벨에 있는 노드 값을 더하고, 합이 가장 큰 레벨을 찾는 문제를 풀었다. 레벨 단위로 값을 처리해야 한다는 점에서 BFS가 먼저 떠올랐지만, 큐에 들어 있는 노드 중 어디까지가 현재 레벨인지 구분하는 과정에서 막혔다.

로컬 테스트를 하면서 LeetCode의 배열 입력과 실제 `TreeNode` 객체가 다르다는 점도 다시 확인했다. 이번에는 레벨 순서 배열을 트리로 바꾸는 builder를 따로 만들어 예제와 경계 조건을 직접 검증했다.

## 1. Maximum Level Sum of a Binary Tree - 레벨별 노드 값의 합 구하기

이진 트리의 루트가 주어지면 각 레벨에 있는 모든 노드 값의 합을 계산한다. 가장 큰 합을 가진 레벨을 반환하되, 같은 최댓값을 가진 레벨이 여러 개라면 가장 작은 레벨 번호를 반환해야 한다.

```python
from collections import deque


class Solution:
    def maxLevelSum(self, root: TreeNode | None) -> int:
        max = float('-inf')
        level = 1
        queue = deque([root])
        max_lev = 0

        while queue:
            level_sum = 0

            for _ in range(len(queue)):
                node = queue.popleft()
                level_sum += node.val

                if node.left:
                    queue.append(node.left)
                if node.right:
                    queue.append(node.right)

            if level_sum > max:
                max = level_sum
                max_lev = level

            level += 1

        return max_lev
```

`queue`에는 앞으로 방문할 노드가 들어 있다. 바깥쪽 `while`문이 시작되는 시점에는 큐에 현재 레벨의 노드만 들어 있으므로, 그때의 `len(queue)`가 현재 레벨의 노드 개수다. 내부 `for`문은 그 개수만큼만 노드를 꺼내 값을 더한다.

노드를 처리하면서 발견한 자식은 큐의 뒤에 추가한다. 이 자식들은 다음 레벨에 속하지만, `range(len(queue))`의 반복 횟수는 `for`문이 시작될 때 이미 결정된다. 따라서 새로 추가한 자식은 이번 `for`문에서 꺼내지 않고 다음 `while` 반복에서 처리한다. 내부 `for`문 하나가 현재 레벨과 다음 레벨의 경계를 만들어주는 셈이다.

처음에는 노드를 하나 꺼낼 때마다 `level`을 증가시켰다. 그러면 같은 깊이에 있는 노드도 서로 다른 레벨로 계산된다. 예제 2에서는 `98693`과 `-89388`을 더해 레벨 3의 합인 `9305`를 만들어야 하지만, 노드별로 비교하면 `98693`만 보고 레벨 3을 최댓값으로 잘못 선택한다. 내부 `for`문에서 같은 레벨을 모두 처리한 뒤 한 번만 `level += 1`을 해야 한다.

시간초과가 발생했던 이유는 큐에 자식이 아니라 현재 노드를 다시 넣었기 때문이었다.

```python
# 잘못된 코드
if node.left:
    queue.append(node)
```

자식이 있는 노드는 큐에서 꺼낸 직후 다시 큐에 들어간다. 같은 노드를 계속 꺼내고 넣게 되므로 큐가 비지 않아 `while queue`가 끝나지 않는다. `queue.append(node.left)`와 `queue.append(node.right)`처럼 실제 자식을 추가해야 한다.

최댓값을 갱신할 때는 `>=`가 아니라 `>`를 사용했다. 두 레벨의 합이 같다면 먼저 방문한 더 작은 레벨을 유지해야 하기 때문이다. `>=`를 사용하면 같은 합을 만날 때마다 더 큰 레벨 번호로 답이 덮어써진다.

모든 노드를 한 번씩 큐에 넣고 꺼내므로 시간 복잡도는 `O(n)`이다. 큐에는 한 레벨의 노드가 가장 많이 들어가므로 공간 복잡도는 트리의 최대 너비를 `w`라고 할 때 `O(w)`다.

### 더 개선한다면

BFS는 문제의 레벨 구조와 바로 맞아서 이해하기 쉽고 시간 복잡도도 이미 최적이다. 다만 너비가 큰 완전 이진 트리에서는 한 레벨의 노드가 큐에 한꺼번에 들어간다. DFS로 `(노드, 깊이)`를 스택에 저장하고 깊이별 합을 누적하면 최대 너비 대신 트리 높이에 비례하는 보조 공간을 사용할 수 있다.

```python
class Solution:
    def maxLevelSum(self, root: "TreeNode") -> int:
        level_sums = []
        stack = [(root, 0)]

        while stack:
            node, level = stack.pop()

            if level == len(level_sums):
                level_sums.append(node.val)
            else:
                level_sums[level] += node.val

            if node.right:
                stack.append((node.right, level + 1))
            if node.left:
                stack.append((node.left, level + 1))

        return level_sums.index(max(level_sums)) + 1
```

`level_sums[0]`에는 레벨 1의 합, `level_sums[1]`에는 레벨 2의 합이 저장된다. 어떤 깊이에 처음 도착했을 때는 새 원소를 추가하고, 이미 방문한 깊이라면 기존 합에 현재 노드 값을 더한다.

마지막의 `max(level_sums)`는 가장 큰 합을 구하고, `index()`는 그 값이 처음 나타난 위치를 반환한다. 따라서 합이 같은 레벨이 여러 개여도 가장 작은 레벨이 선택된다. 리스트 인덱스는 0부터 시작하므로 실제 레벨 번호를 반환할 때 1을 더한다.

재귀 DFS로도 같은 방식으로 구현할 수 있지만, 문제의 노드 수는 최대 10⁴개다. 한쪽으로 치우친 트리에서는 Python의 기본 재귀 깊이를 넘을 수 있으므로 명시적인 스택을 사용했다. 모든 노드를 한 번씩 처리하므로 시간 복잡도는 `O(n)`, 스택과 레벨 합 리스트에 필요한 공간은 트리 높이를 `h`라고 할 때 `O(h)`다. 넓고 균형 잡힌 트리에서는 BFS보다 적은 공간을 사용할 수 있지만, 한쪽으로 치우친 트리에서는 `h = n`이므로 최악의 공간 복잡도는 `O(n)`이다.

## 2. 스스로 묻고 답한 질문들

### Q. `for _ in range(len(queue))`를 도는 동안 큐의 길이가 바뀌어도 괜찮을까?

괜찮다. `range(len(queue))`를 만들 때 `len(queue)`가 한 번 계산되어 반복 횟수가 정해진다. 반복 도중 자식을 큐에 추가해 길이가 늘어나더라도 현재 `for`문의 횟수는 늘어나지 않는다. 새로 추가된 자식은 다음 바깥쪽 `while` 반복에서 처리된다.

### Q. 최댓값의 초깃값은 왜 `0`이 아니라 음의 무한대일까?

노드 값은 음수가 될 수 있고, 모든 레벨의 합이 음수일 수도 있다. 초깃값을 `0`으로 두면 어떤 레벨도 `0`보다 크지 않아 답이 갱신되지 않는다. `float('-inf')`로 시작하면 첫 번째 레벨의 합이 어떤 음수여도 반드시 비교 결과가 참이 된다.

### Q. LeetCode의 `root = [1, 7, 0, ...]`을 함수에 그대로 전달하면 왜 안 될까?

배열은 LeetCode가 입력을 보여주는 직렬화 표현이다. 실제 호출에서는 플랫폼이 이 배열을 연결된 `TreeNode` 객체들로 변환한 뒤 루트 노드를 전달한다. 로컬 테스트에서는 같은 변환 과정이 없으므로 builder로 트리를 직접 만들어야 한다. 또한 LeetCode 표기의 `null`은 Python 코드에서 `None`으로 적어야 한다.

### Q. DFS는 노드를 레벨 순서로 방문하지 않는데 어떻게 레벨 합을 구할 수 있을까?

방문 순서와 합산 기준은 별개다. 스택에 노드와 함께 깊이를 저장하면, 어떤 순서로 방문하더라도 같은 깊이의 값은 동일한 `level_sums[level]`에 더해진다. BFS는 같은 레벨을 한 번에 처리하고, DFS는 떨어져 방문한 같은 레벨의 값을 같은 칸에 누적한다는 차이가 있다.

### Q. DFS 풀이가 항상 BFS 풀이보다 더 좋은가?

그렇지는 않다. BFS는 문제에서 요구한 레벨 단위 처리를 코드 구조로 바로 표현하므로 의도가 명확하다. DFS는 너비가 큰 트리에서 보조 공간을 줄일 수 있지만, 노드마다 깊이를 함께 저장하고 탐색이 끝난 뒤 최대 합을 다시 찾아야 한다. 트리의 모양과 코드의 명확성까지 고려해 선택해야 한다.

## 정리하며

이번 문제에서 가장 중요했던 것은 큐에 노드가 들어 있다는 사실만으로는 레벨이 자동으로 구분되지 않는다는 점이었다. `while`문이 시작될 때의 큐 길이를 저장하고, 그만큼을 내부 `for`문에서 모두 처리해야 한 레벨을 정확히 묶을 수 있었다.

시간초과의 원인도 BFS 자체가 느려서가 아니라 현재 노드를 다시 큐에 넣은 작은 구현 실수였다. 큐가 반복할 때는 매 단계에서 어떤 항목이 제거되고 어떤 항목이 새로 추가되는지 직접 따라가보는 것이 도움이 됐다. 또한 `>`와 `>=`의 차이가 동점일 때 가장 작은 레벨을 선택한다는 조건으로 이어진다는 점도 확인했다.

DFS로 다시 작성해보니 레벨 순서로 방문하지 않더라도 깊이를 상태로 함께 전달하면 같은 결과를 만들 수 있었다. 같은 문제를 BFS와 DFS로 각각 풀어보면서, 탐색 순서보다 필요한 상태를 어떻게 기록할지가 더 중요하다는 점을 정리할 수 있었다.
